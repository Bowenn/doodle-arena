# Doodle Arena: roadmap

How to use this file:

- Stages run roughly in order. After Stage 1, two tracks run in parallel.
- Each task has an ID, such as 2.3. Start a task in Claude Code with `/milestone 2.3`.
- Each stage ends in a milestone (M1 to M6) with exit criteria. A milestone is reached when every criterion is checked.
- Tick tasks (`[x]`) as they finish, and record measured numbers in the evidence log at the end.
- The estimates assume agents write most of the code. Correctness tests and measurements take longer than code; plan for that.

## Overview

| Stage | Goal | Track | Estimate | Depends on | Milestone |
|---|---|---|---|---|---|
| 1. Foundations | Repo, local stack, contracts, auth, CI, telemetry | Both | Day 1 | – | M1 |

## Stage 2: Game core (Track A, Days 2–3)

- [x] **2.2 Game server core**: the room actor, WebSocket handling with tickets, the round state machine, word lists, scoring, hints, the per-player token bucket, and the JSON protocol from the design doc.

- [x] **2.3 Web room UI**: canvas with batched strokes, guess box, scores and timer.
  - Lobby page and `/rooms/<id>` invite links; a pure reducer over server messages; strokes batched every 50 ms (`VITE_STROKE_BATCH_MS`, `?batch_ms=`) with widths in normalized units; reconnect with a fresh ticket, `last_seq` and jittered backoff. Checked live on 2026-10-16 with one signed-in browser and two scripted players, through two full matches.
- [x] **2.4 Events out**: the stroke log upload (claim check), `RoundFinished` and `MatchFinished`.
  - Decided 2026-10-16: a bounded in-memory queue that drops new events when full (2.5's Redis Stream can become the durable outbox), a fixed 4:3 canvas (800 x 600), and every round published but no match without a finished round.
- [x] **2.5 Reliability**: the Redis Stream event log with explicit `seq` IDs, snapshots, reconnect with resume, the lease and fencing token through Lua, and failover through the lobby, with two game-server instances in Compose. The humans decide ADR 0002 first.
  - ADR 0007 is decided (2026-10-16): forced takeover with fencing tokens. Write-then-broadcast, snapshots at phase changes plus in-phase events on restore, resume by replay, and a lobby reassigner. Drill: `scripts/drills/failover.py kill|pause`.
- [x] **2.6 Shared canvas and leaderboard**: two drawers per round with own-stroke undo; a weekly leaderboard built from `MatchFinished`.
  - 2.6b, the weekly leaderboard, is done (decided 2026-10-16: rank by the sum of match scores per ISO week, names from a lobby name cache, no contract change). The lobby consumes `game.matches.v1` as group `lobby-leaderboard`, counts each match once with one Lua script (`SET NX` on the `match_id`, then `ZINCRBY`), and serves `GET /api/lobby/leaderboard`; the web app has a `/leaderboard` page. 2.6a (the shared canvas) is a separate PR.
  - 2.6a, the shared canvas, is done (decided 2026-10-16: the first drawer picks the word, no contract change): from 4 present players two drawers share the canvas; the first picks the word (no contract change), both draw and undo only their own strokes, and each earns the drawer points.

## Stage 4: Economy (Track B, plus Track A for 4.7; Days 5–6)

- [x] **4.1 Ledger core**: accounts, balances, transactions and entries (Flyway), system accounts, and the reconciliation job with its metrics.
  - Done 2026-10-18: `LedgerService.post` (idempotency key with `ON CONFLICT`, one sorted `FOR UPDATE`, merged postings), Postgres-side checks (deferred sum-to-zero trigger, append-only triggers, `CHECK` on `balances.owner_type`), the reconciliation job (`market.ledger.imbalance`, `market.ledger.mismatched_accounts`; `market.ownership.violations` comes with 4.2), and JWT verification with `GET /api/market/wallet` and `/wallet/transactions`.
- [x] **4.2 Ownership**: mint from `DrawingApproved`, record authors, serve the ownership history.
  - Done 2026-10-18: a Spring Kafka consumer (group `marketplace`) mints idempotently by drawing id (ownership primary key), records authors in order and an append-only `MINT` event, retries outages on the same offset and skips only records that can never succeed; `market.ownership.violations` checks ownership against its provenance; `GET /api/market/drawings/{id}/ownership-history`.
- [x] **4.3 Listings and purchase**: create and cancel listings, the purchase transaction, `Idempotency-Key` handling, the outbox publisher.
  - Done 2026-10-18: listings (owner only, one active per drawing, strict integer prices), the purchase in one transaction (listing → ownership → balances, ledger key `sale:<listing_id>`), idempotency keys with a leased claim and a fenced completion that remember business outcomes (ADR 0012), and the in-process outbox relay for `ListingCreated`, `ListingCancelled` and `SaleCompleted`. Royalties stay in 4.6 (the seller gets the whole price).
- [x] **4.4 Rewards**: pay round rewards from `MatchFinished`.
  - Done 2026-10-18: one ledger transaction per match (`reward:<match_id>`, all or nothing, ties share a placement's amount, 2+ players), a `CoinsCredited` per player through the outbox, and the `game.matches.v1` consumer with the drawings consumer's skip and retry rules.
  - Prerequisite done 2026-10-17: the game server's durable outbox (ADR 0009), so every finished match reaches Kafka at least once, with the same `event_id` on every delivery. The rewards consumer dedupes by `match_id`.
- [x] **4.5 Stripe coin packs**: Checkout, webhook signature verification, dedupe and crediting; local testing with the Stripe CLI.
  - Done 2026-10-18: packs in config priced inline, checkout with an `Idempotency-Key` (ADR 0012) and a derived Stripe idempotency key, a webhook that verifies `Stripe-Signature` and credits the coins recorded at checkout once (Stripe event id and ledger key `stripe:<session_id>`), tests against `stripe/stripe-mock`. Setup steps in `docs/setup.md` ("Stripe").
- [x] **4.6 Royalties**: the royalty split and its rounding rule.
  - Done 2026-10-18: 10 % floored to the authors who are neither the seller nor the buyer, whole-coin shares with the remainder to the first in drawing order, zero shares left out; posted in the purchase's ledger transaction and listed in `SaleCompleted.royalties`.
- [x] **4.7 Notifier and API keys** (Track A): API keys in auth; endpoint registration, signing, retries, the dead-letter queue and the delivery log in the notifier.
  - Done 2026-10-18 (ADR 0014): API keys in auth (verified on internal port 9091, revoked on refresh-token theft); the notifier's Postgres queue and log, owner-only fan-out of `SaleCompleted` and `CoinsCredited`, encrypted signing secrets, the SSRF-safe sender, full-jitter retries, `DEAD` and `DeliveryDead`; a `webhook-receiver` test service and `scripts/drills/webhooks.py`.
- [x] **4.8 Web**: wallet, buying coins, the marketplace, "my drawings", and developer settings.
  - Done 2026-10-18: `/wallet` (balance, history, coin packs through Stripe Checkout, polling until the webhook's coins land), `/market` (listings with thumbnails from a new assets `?ids=` lookup, Buy with confirmation), `/my-drawings` (owned drawings from a new marketplace `owner=me` endpoint; list or cancel), ownership history with sale prices on a drawing's page, and `/developer` (API keys and webhook endpoints, which the notifier now also manages with the session's token). One `Idempotency-Key` per money action, reused only while its outcome is unknown.

**Stage 4 review follow-ups** (decided by Bowen, 2026-10-18, D43; each its own PR, plan first):

- [x] **4.R1 Checkout outside a database transaction** (money path, plan mode): claim the `Idempotency-Key`, call Stripe with no transaction open, then record the checkout and complete the key in one short transaction, as ADR 0012 describes. Today `CheckoutService.start` holds a pool connection for the whole Stripe call.
  - Done 2026-10-18: a call step in `IdempotencyService.execute` that runs between the claim and the completing transaction; the checkout calls Stripe there and records the session afterwards. The Stripe idempotency key is now derived per claim, because Stripe replays a saved 500 for 24 hours (found while planning; Bowen chose per claim). `CheckoutTransactionTests` runs against a stub that saves responses per key like Stripe.
- [x] **4.R2 Revoke webhooks with the credentials** (`proto/` change, ADR): auth publishes an event when it revokes a user's credentials on refresh-token theft, and the notifier disables all that user's endpoints and cancels their pending deliveries; re-enabling one rotates its secret. Today endpoints, whether made with an API key or a session, keep receiving the user's sales and credits.
  - Done 2026-10-18 (ADR 0015): `CredentialsRevoked` on `auth.users.v1`, written once per refresh-token family in the revoking transaction and published by a new `auth-relay` process; the notifier (group `notifier-auth`, from the earliest offset) disables the user's endpoints and keeps a watermark that refuses older sessions and API keys, re-checked under the owner's lock; Enable rotates the secret. Two security-review findings fixed on the way (replays re-triggering the theft response; cached keys and a check-then-insert race). `scripts/drills/credential_theft.py`.
