# Interview notes

Talking points collected after each task (the `/milestone` skill appends to this file). For each one: the problem, the design choice, the alternative that was rejected and why, and how the design fails.

Read this before interviews, and practice with the interview drill prompt in `docs/KICKOFF_PROMPT.md`.

## Stage 1: Foundations

### 1.1 Repo skeleton and local stack

- **Database per service, enforced rather than just agreed.** One Postgres server, but each service has its own database and its own login role, and `PUBLIC` loses `CONNECT`. The `auth` role gets "permission denied" on `marketplace`. Rejected: a shared user with schemas, which is easier but lets one service quietly read another's tables. Failure mode: the Postgres server is still a shared resource, so one service's heavy query can slow every other service. Isolation is logical, not physical.
- **The gateway resolves services at request time.** Nginx normally resolves upstream host names once at startup and refuses to start if one is missing. With Docker's DNS resolver and a variable in `proxy_pass`, the gateway starts and keeps routing while a service is down, and returns 502 only for that service (tested by stopping `ai`). Trade-off: a DNS lookup every 10 seconds per name, and the resolver address is environment-specific (`127.0.0.11` in Docker; different on ECS).
- **Health checks without a shell.** The Go services ship in distroless images (no shell, no curl, smaller attack surface), so the binary has a `healthcheck` subcommand that calls its own `/healthz`. The JRE image has no curl either, so the marketplace image installs it. Alternative: a full base image, which is simpler but larger and has more CVEs to patch. Liveness only: `/healthz` doesn't check dependencies, so a service whose database is down still reports healthy. Readiness checks come later.
- **Don't log what you can't un-log.** The gateway logs `$uri`, not `$request_uri`, because query strings carry OAuth codes and state. This was verified by sending `?code=SECRET123` and finding no match in the logs. Logs get shipped, indexed and kept, so a secret in a log is a leaked secret.
- **Pin to match where you'll deploy, not just to "latest".** Kafka is pinned to 4.2.2, not the newer 4.3, because Amazon MSK stops at 4.2. MongoDB is pinned to 8.0 because DocumentDB is MongoDB-8.0 compatible. Redis 8 runs locally, but the code sticks to commands that ElastiCache's Redis 7 and Valkey also support. Local and cloud can still drift, so each version bump is its own commit.

### 1.2 Contracts

- **One wrapper per topic, not a type header (ADR 0004).** Protobuf bytes don't say what type they are, and some topics carry two events. A `oneof` wrapper puts "what can appear on this topic" into the contract, where `buf breaking` checks it. A header lives outside the schema, so a typo only fails at consumption time. Failure mode: a consumer built before a new event type sees an empty `oneof`. The rule is to log it, count it and move on, never to crash or block the partition. A test checks that unknown field 99 decodes to "no case set".
- **No schema registry.** Compatibility is enforced in CI (`buf breaking` against `master`), not at produce time, which saves running another stateful service. Trade-off: a producer built from an unmerged branch could publish an incompatible message to a shared environment. With many teams or external consumers, a registry would earn its keep.
- **Claim check for big payloads.** `RoundFinished` carries only the object key of a gzipped `StrokeLog` in S3. Kafka messages stay small, and there's no "have I seen every stroke yet?" ordering problem. The stroke log is protobuf rather than JSON, so its format is versioned and lint-checked like the events. The cost: it isn't readable with `zcat`, and objects expire after 7 days, so assets must fetch the log before then.
- **Committed generated code, built in three languages on every run.** `make proto` regenerates with pinned remote plugins (identical output everywhere, and running it twice changes nothing), then compiles the Go, Java and Python code. Golden files written from Go are decoded in Python, which proves the wire format agrees across languages, not just that each language compiles.
- **Keys and partitions.** Events are keyed by `room_id`, `drawing_id`, `user_id` or `endpoint_id`. franz-go uses the same murmur2 partitioner as the Java client, so one room's events land on one partition in order, whichever language produced them. Replaying a match with `-match-id` lands on the same partition, which is what idempotent consumers will be tested against.

### 1.3 Auth and gateway

- **Refresh-token rotation with reuse detection.** Every refresh swaps the token for a new one in the same family. If an already-used token comes back, someone holds a copy, so the whole family is revoked and both thief and user must sign in again. The row is locked with `SELECT … FOR UPDATE`, so 10 concurrent refreshes of one token produce exactly 1 winner, and the other 9 count as reuse (a test checks this). Failure mode: a legitimate client that refreshes twice at once logs itself out. That's why the web app refreshes single-flight, which also covers React StrictMode's double effects in development. Rejected: a grace window, friendlier with several tabs but it blurs theft detection.
- **A bug the tests caught: rollback would undo the revocation.** `rotate()` first raised an exception inside the transaction when it detected reuse, which rolled back the family revocation it had just written. The route happened to work around it, but the concurrency test, written naturally, left 2 live tokens. The fix makes `rotate()` return an outcome instead of raising, so the security-critical write always commits. Lesson: never signal an expected business outcome with an exception that crosses a transaction boundary.
- **Login CSRF and PKCE without server-side state.** The `state`, OIDC `nonce` and PKCE verifier live in a short-lived, HMAC-signed, HttpOnly cookie scoped to the callback path. Matching `state` to the cookie binds the login to this browser, so an attacker can't log you into their account by sending you their callback URL. The `nonce` binds Google's ID token to this login. PKCE makes a stolen authorization code useless without the verifier. Rejected: a database table, which would add single-use enforcement that Google already provides.
- **Where tokens live.** The access token (15 minutes, RS256) lives only in JavaScript memory, never in localStorage, which XSS can read. The refresh token is an HttpOnly, SameSite=Strict cookie scoped to `/api/auth`, so page scripts can't read it and other sites can't send it. `/refresh` and `/logout` also check `Origin`. Trade-off: a page reload costs one refresh call.
- **Coarse limits at the edge, fine ones in the service.** Nginx `limit_req` is a leaky bucket per IP: 20 r/s on the API, 5 r/s on sign-in and refresh, with a JSON 429 and `Retry-After`. A burst of 40 gets 29 rejections. Behind a load balancer the client IP must come from `X-Forwarded-For`, or every user shares one bucket. Per-player limits (guesses) need game context, so they live in the game server.

### 1.4 CI

- **CI runs exactly what developers run.** Every job sets up a toolchain, then calls `scripts/lint.sh` and `scripts/test.sh`, the same scripts as `make`. No build or test logic is duplicated in YAML, so "green locally, red in CI" can only mean an environment difference, not a different command. Rejected: hand-written steps per workflow, which drift from the Makefile within weeks.
- **Per-service workflows on reusable building blocks.** Ten thin workflows, one per service, each with a path filter, call five reusable workflows (one per language, plus Docker). A change to `services/auth` runs only auth's lint, test and image build, which matters on a private repo with a minutes quota. Trade-off: a workflow skipped by its path filter never reports, so it can't be a required check. Branch protection would need an always-run gate job, which a single matrix workflow gives for free.
- **Contracts are checked twice.** `buf breaking` compares the PR against its base commit, so a renumbered or retyped field fails before anyone depends on it. Then CI regenerates all three languages and fails if the committed code differs, so nobody can merge a `.proto` change without its generated code, or edit generated code by hand.
- **Supply-chain hygiene.** Every action is pinned to a 40-character commit SHA, because a tag like `v7` can be moved to malicious code and a SHA can't. Dependabot keeps the pins current. Workflows get read-only tokens, checkouts don't persist credentials, and event data reaches shell scripts only through environment variables (no `${{ }}` inside `run:`), which closes the classic workflow-injection hole.
- **Cost-aware integration testing.** The full-stack smoke test (`make up` plus `make smoke`, about 5 minutes) runs only when the stack itself changes, on `master`, and on demand. Unit and Testcontainers integration tests run on every relevant PR. That spends minutes where breakage is likely.

### 1.5 Observability baseline

- **One request, one trace, across languages.** The gateway (Nginx with `ngx_otel_module`) starts or continues a W3C `traceparent` and passes its own span id upstream, so the Go, Python and Java spans become its children. `make telemetry-check` sends a request with a known trace id and passes only if Tempo has the gateway and auth spans, Loki has auth's log line with that `trace_id`, and every service exports metrics. CI runs it, so a broken pipeline fails a PR instead of being found during an outage.
- **Logs join traces through `trace_id`.** Every JSON log line carries `trace_id` and `span_id` when a span is active. The same records also go over OTLP to Loki, where Grafana links "related logs" from a span and jumps back from a log line to its trace. stdout stays the source of truth for container logs (CloudWatch in AWS), and OTLP gives the correlation. The gateway's logs are the gap: Nginx can't export logs over OTLP, so its access log only carries the ids for now.
- **Three languages, three instrumentation styles, one contract.** Go uses the SDK in code (`otelhttp`, an `slog` fan-out to the OTLP bridge); Java uses the zero-code agent, checksum-pinned in the Dockerfile; Python uses explicit setup instead of `opentelemetry-instrument`, because our logging config replaces root handlers and gunicorn forks after the agent starts its export threads. All three read the same `OTEL_*` environment and stable HTTP semantic conventions (`OTEL_SEMCONV_STABILITY_OPT_IN=http`), so one RED dashboard covers every service.
- **Bugs the end-to-end check caught.** Its request first got rate-limited by the gateway (`make smoke` had just drained the bucket), which proves the limit works but hid the trace; the fix retries with a fresh trace id per attempt. And the Python SDK exported no metrics from services without traffic. Adding process runtime metrics gives every service a heartbeat (`target_info`), the way Go and the JVM already had.
- **Cardinality and noise.** No IDs in metric attributes (one series per room would melt Prometheus). Health checks and dev-server assets aren't traced, because they'd bury real traffic. The exception is the Java agent, which has no simple path filter, so marketplace's health check produces a small trace every few seconds until tail sampling (Stage 6) drops it.

### 1.6 README

- **The README was tested like code.** A fresh clone of the branch followed the quick start word for word, under a separate Compose project, so fresh volumes and no shared state: `cp .env.example .env`, `make up`, `make smoke`, `make telemetry-check`. Everything passed in about 45 seconds of startup. Docs that nobody runs rot; the check found a real gap before anyone hit it.
- **The gap: a hand-made `.env` kept placeholder passwords.** The natural first step, copying `.env.example` to add Google credentials, left literal `change-me` values, because the start script only generated secrets when it created `.env` itself. It now replaces any remaining placeholder and never touches real values, and running it twice changes nothing.
- **What goes in the README and what doesn't.** It answers "what is this, how do I run it, where do I read more" in a few minutes, and links to the design doc, roadmap and ADRs for depth. The troubleshooting section holds the real gotchas from Stage 1 (port 15432, `redirect_uri_mismatch`, Loki refusing writes on a full disk), because those cost hours to find.

## Stage 2: Game core

### 2.1 Lobby

- **Join tickets that only the lobby can mint (ADR 0005).** A WebSocket can't carry the JWT safely (URLs end up in logs), so the lobby hands out a 60-second ticket naming the user and the room. It's signed with Ed25519: game servers hold only the public key, so a compromised game server can verify tickets but can't forge one for another room. Rejected: a shared HMAC secret, where every verifier is also a signer, and rotation means updating every service at once. Failure mode: a short expiry alone doesn't stop replay within 60 seconds, so the game server also records each ticket id with `SET NX` (task 2.2). That puts the lobby on every reconnect path, because each connection needs a fresh ticket.
- **Liveness through key expiry, not a reaper.** Each heartbeat rewrites `lobby:server:{id}` with a 6-second TTL (three missed beats). A dead server simply disappears from Redis, so a failure needs no detector and no cleanup job, and a restarted lobby loses nothing. Trade-off: the lobby can't tell "dead" from "partitioned from the lobby but still serving players". That's why room ownership itself is a lease with fencing tokens (task 2.5), not the registry.
- **Allocation is an idempotent RPC with a deadline and fallback.** `AllocateRoom` has a 2-second deadline. On `RESOURCE_EXHAUSTED` or `FAILED_PRECONDITION` (full or draining) the lobby tries the next least-loaded server, up to three. A retry after a timeout is safe because the game server treats a room id it already holds as success. The room is stored only after a server accepted it, so a failure leaves nothing behind. A server that heartbeats but doesn't answer would otherwise stay "least loaded" forever (it never gets rooms) and cost every create its full deadline, so it goes to the back of the list for 10 seconds. Failure mode: if the lobby crashes between the RPC and the write, a game server holds a room nobody can find; it closes it when nobody joins.
- **The lobby doesn't enforce room capacity.** It sees player counts in heartbeats up to 2 seconds old, and it can't tell a new player from someone reconnecting, who needs a fresh ticket under single-use tickets. So the game server, which knows the members, decides. The lobby uses counts only for listing and for quick play, which picks the fullest waiting room so rooms fill instead of spreading players thin.
- **Unauthenticated internal RPCs are an attack surface.** Heartbeats aren't authenticated yet, so a rogue process on the internal network could register itself. Two mitigations: `ws_address` must be a gateway path under `/ws` (never a full URL), so a fake server can't send players' tickets to another host; and a heartbeat refreshes only rooms whose stored `server_id` matches, checked atomically in a per-room Lua script. The real fix is mTLS between services, which is still an open decision.

- **A cached connection is a cached DNS answer (bug found in Stage 2).** The lobby kept one gRPC connection per game server. After the containers were recreated and swapped IP addresses, the connection for game-server-1 reached game-server-2. The lobby logged the mismatched id but stored the room anyway, so every join failed until a restart. The fix has two halves: every `AllocateRoom` names its target, and the wrong server refuses; and the lobby never records a room the target didn't confirm, dropping the connection to look the name up again. Lesson: verify identity at the application layer when addresses are reused. The same problem shows up with pooled DB connections after a failover, or a load balancer's stale targets.

### 2.2 Game server core

- **One goroutine per room, and a pure core inside it.** All of a room's inputs (joins, leaves, guesses, strokes, timer ticks) go through one FIFO inbox, so "who guessed first" is simply the first guess the actor reads. There are no locks to get wrong. The rules live in a `Game` type with no goroutines, I/O or clock, so tests drive it with explicit times. The M2 test fires 7 correct guesses from 7 goroutines at once (50 runs with `-race`): exactly one is first, and all 8 clients see the same order. Rejected: a mutex around shared room state, which makes fairness depend on lock scheduling and is hard to reason about. Failure mode: a slow room is slow for everyone in it. That's why the actor never does network I/O; it only queues bytes.
- **Timers as deadlines, not callbacks.** The actor keeps one timer pointed at the game's next deadline. A tick only asks the game to fire what is due at "now", so a stale or early tick does nothing. Tests use a fake clock and a probe message instead of sleeping, so they are fast and deterministic. It's also what task 2.5 needs: deadlines are absolute timestamps that a new owner can restore from a snapshot.
- **A slow client must never slow the room.** Each socket has a 128-message queue and one writer goroutine. Sending never blocks: a full queue closes that client with 1013, and it can reconnect for a fresh view. Rejected: blocking writes from the actor, which lets one bad phone connection freeze a whole room. Trade-off: on a congested network, a client is dropped rather than sent stale data, which is right for a live game but would be wrong for a chat history.
- **Where secrets leak: the obvious and the sneaky paths.** The word reaches a client in exactly two ways: `your_word` for drawers, and views once the round has ended. One function sends the private state, and that's what gets audited. The sneaky path was chat: a guess like "is it zebras?" contains the word, so it is answered privately and never broadcast. Drawers, and players who already guessed, can't chat during a round. The M2 leak test reads every byte sent to guessers, including a late joiner and a reconnect, and fails when a leak is planted.
- **Small things that would have been bugs.** Go's JSON decoder fills a fixed-size array with zeros, so a point decoded as `[3]int` would turn `[1,2]` into `[1,2,0]`; points are decoded as slices and checked. The gateway forwards `Host` without the port, so the WebSocket library's same-origin check would have rejected every browser; allowed origins are configured explicitly. `http.Server.Shutdown` doesn't track hijacked WebSockets, so the handler keeps its own `WaitGroup`; the race detector found that `Add` and `Wait` needed a lock between them.

### 2.3 Web room UI

- **The client is a mirror, not a referee.** Room state is a pure reducer over server messages: `welcome` replaces it, and events apply only when their `seq` is newer than the last one applied. Scores don't move when a "correct" chat line appears; they change when `round_ended` says so. The guesser's word line is the server's mask, and the drawer's word comes only from the private `your_word`. Rejected: computing scores or timers locally for snappier feedback, which makes two clients disagree the moment one misses a message. Failure mode: the UI is exactly as fresh as the socket, so a dead socket shows a stale room. That's why the connection status is always visible.
- **Optimistic drawing without a second source of truth.** The canvas has two layers. The base layer paints only the server's broadcast strokes, so every player, the drawer included, sees the same picture. The drawer's in-progress stroke goes on an overlay right away and disappears when the server's copy (its `done` batch) arrives, or when a `welcome` resets the state. A stroke the server refused (wrong phase, canvas full) never reaches the base layer, so the client can't show a picture the room doesn't have. Rejected: drawing straight into the shared canvas, where a rejected stroke would stay on one screen.
- **Batching is the throughput knob.** Pointer events can fire 120 times a second; points go out every 50 ms, or at once at 512 points, which is the protocol's cap. That's at most about 20 messages a second per drawer, and each is one fan-out on the server. The interval comes from `VITE_STROKE_BATCH_MS`, or `?batch_ms=` for one experiment, so the latency-versus-load trade-off can be measured instead of guessed. `getCoalescedEvents()` keeps the points the browser merged, so fewer messages doesn't mean jaggier lines. Painting is incremental: the reducer only appends or removes batches, so the painter draws new batches only while the batch it drew last is still in place, and repaints from scratch otherwise (undo, a new round).
- **Reconnect is a protocol, not a retry loop.** Tickets are single-use, so every attempt goes back to the lobby for a new ticket and the room's current URL (after a failover that URL names another server). The client sends `last_seq`, backs off with jitter from 0.5 s to 8 s so a server restart doesn't get a thundering herd, and gives up after about a minute, which is how long the room keeps a seat. Some closes are final: room full, no such room, a bad first message, and 4009 ("you connected elsewhere"), because two tabs that both retry would keep kicking each other off. A gap in `seq` means a lost message, so the client reconnects and lets the server resend the state rather than guessing.
- **What's not solved yet.** The timer counts down on the local clock to the server's absolute deadline, so a skewed clock shows a wrong countdown (the server still decides; a `server_time` in `pong` would fix the display). The round-trip time is measured from pings and shown, but exported as `web.ws.rtt` only with browser telemetry in task 5.4. The UI is tested with a fake WebSocket and checked against the real stack with one browser plus scripted players; M2's three-browser match needs three people. The live game found what the unit tests couldn't: the chat feed's `scrollIntoView` also scrolled the page, so every incoming chat line moved the canvas under the drawer's pointer mid-stroke. A game-server restart during the test also showed that new rooms became unjoinable until the lobby restarted (its cached gRPC connection reached the wrong server), which is a lobby bug for a later task.

### 2.4 Events out

- **The claim-check pattern, and its ordering rule.** A round's strokes can be hundreds of KB, so they go to object storage (`round-logs/<match_id>/<round_no>.binpb.gz`, a gzipped protobuf), and `RoundFinished` carries only the key. The upload must finish before the event is produced, so a consumer never fetches a key that doesn't exist yet. The key is deterministic, so a retried upload overwrites the same bytes. Rejected: streaming strokes on their own topic, because the consumer could never know when it had all of them. Failure mode: the object's 7-day expiry. A consumer that falls more than a week behind finds the event but not its strokes.
- **I/O never runs in the room's goroutine.** The actor hands a finished round to a publisher through a non-blocking call; one worker goroutine with a bounded queue does the S3 upload and the Kafka produce. When Kafka is down, the queue fills and new events are dropped, logged with their ids and counted (`game.events.published{result=dropped}`), instead of freezing every room on the server. Rejected: blocking the actor (one broker outage stops every game) and an unbounded queue (an outage becomes an out-of-memory crash that loses everything). The weakness at the time: the queue was in memory, so a crash lost up to a queue's worth of events. That is fixed by the outbox (ADR 0009, below).
- **At-least-once, stated precisely.** Each event gets its UUID when it is queued, so every retry reuses it. franz-go's idempotent producer stops its own retries from writing duplicates, and `acks=all` waits for the in-sync replicas. A surprise from the outage test: with idempotence on, franz-go won't cancel a record that might already be in flight. A synchronous produce sat through a 40-second outage with no regard for its deadline. So the publisher produces asynchronously, stops waiting at the event's deadline, and never resends after a timeout: the old record may still be delivered, and resending would guarantee a duplicate. A late delivery or a retried definite failure can still publish twice, so consumers deduplicate on `event_id` or the natural key ((match_id, round_no) and match_id). Exactly-once would need Kafka transactions plus transactional consumers, a lot of machinery for events whose consumers must be idempotent anyway.
- **One trace from the room to the consumer.** The room records an instant `game.round.end` span and passes its context along with the work. The publisher's `game.round.publish` span is its child, and it contains the `S3.PutObject` span (otelaws) and the Kafka producer span. franz-go's kotel hook writes that producer span into the record's `traceparent` header, so the consumer's trace continues the same tree. A Testcontainers test against the real `apache/kafka` and SeaweedFS images checks that chain hop by hop.
- **What the producer decides and what it doesn't.** A match that ended before any round finished (players left during the countdown) is never published, so an aborted match can't earn rewards. Anything stricter, like a minimum number of players or correct guesses, is the marketplace's reward policy: the event reports facts (placements and scores), not payouts. Known gap: a match with one very short round still produces `MatchFinished`, so the reward rules (task 4.x) and wash-trading detection (Stage 6) must handle it.

### ADR 0006: internal gRPC authentication

- **Choosing not to authenticate, on purpose.** The lobby and game servers trust each other over plaintext gRPC, and in AWS security groups open port 9090 only between them. The threat is written down: any process inside the network can send heartbeats as any game server, or drain every server. It needs code already running inside, and it costs availability, not room access (join tickets decide that) or money (coins are closed-loop). Rejected for now: mTLS and signed service tokens. Both were prototyped and both work, but they protect against a threat that doesn't exist yet, at the price of keys or certificates in every environment. The decision flips on public users, real money, a deployment where security groups can't separate services (Compose on EC2), or new gRPC callers.
- **mTLS versus tokens, measured rather than guessed.** In the spike, mTLS cost 16 µs per call on an open connection (15.5 without it) but 790 µs per new connection; tokens cost 54 µs on every call (an Ed25519 verify plus JWT parsing) and little per connection. mTLS was less code (+400 lines, standard library only) than tokens (+631), because tokens rebuild what TLS already gives: binding keys to identities, caching, claim checks. Tokens gave far clearer errors: a bad certificate fails in the handshake as `Unavailable`, before any interceptor runs, so it looks exactly like a network outage.
- **Tokens on plaintext authenticate the caller, not the message.** A bearer token doesn't cover the request body, so anyone on the path can keep a valid token and change the heartbeat. Containers have `NET_RAW` by default, so on one Docker bridge network this isn't hypothetical. mTLS also gives integrity, and proves to each caller that it reached the right server.
- **Identity isn't authorization.** The spike found two holes that either mechanism alone leaves open. The lobby's own credential was valid at the registry, so roles need checking too. An authenticated `game-server-2` could report `game-server-1`'s address as its own `control_address`, so the address must be bound to the caller as well. Authentication tells you who is calling; every field that names a resource still needs its own check.

### 2.5 Reliability

- **Fencing tokens make a forced takeover safe (ADR 0007).** A lease alone isn't enough: a paused process can wake up believing it still owns the room. Every takeover increments a counter, and every write (events, snapshots, lease renewals, ticket redemptions) is a Lua script that checks `lease == server:token`. So a new owner can take the room immediately instead of waiting for the old lease to expire. The zombie drill shows it: the paused owner wakes, its next renewal is rejected within 0.2 s, and it tells its clients the room moved. Rejected: waiting for the lease to expire, which adds about 5 s and relies on the old owner stepping down.
- **Write, then broadcast.** The actor commits each step's events to the Redis Stream before any socket sees them. That one rule makes resume and takeover exact: nothing a client saw is missing on the new owner, and a client that resumes gets precisely the seqs it missed (every drill run: 0 gaps, 0 duplicates). The cost is one Redis round trip per step before broadcasting; the failure mode is a room that stops when Redis is down, which is consistency over availability, chosen deliberately.
- **Snapshot plus events, verified by a property test.** Snapshots are taken at every phase change and every 200 events, so the events after a snapshot only change a room within its phase, and restore needs an `apply` for about nine event types. A property test plays 20 random 1500-step games and checks after every few steps that snapshot plus events rebuild the live state exactly; a planted bug in `apply` fails all 20. That turned "replay should work" into evidence. One subtlety: after a takeover everybody is disconnected, so a 15-second grace keeps the match from ending before they resume.
- **The lobby had to learn which rooms a server held.** Heartbeats expire with the server, so a separate index of rooms by server survives it. A reassigner, with one lobby at a time holding a Redis lock, moves rooms of dead servers and rooms a restarted server no longer reports. A security review caught two races: a pass could outlive its lock, and a room just moved could be moved again before its new server's first heartbeat. The fixes were a compare-and-set move on `server_id` and a grace counted from the placement time, not the creation time.
- **Measure it, don't assume it.** Killing a room's server mid-drawing: players resume on the other instance in 5.1–7.8 s (7 runs), under the 10-second target, with about 6 s of that being heartbeat detection. The pause drill showed a gap no unit test would: a frozen server keeps its clients' TCP sockets open, so clients only move once the zombie wakes up and fences itself, or once they notice the dead socket. Client-side liveness (no pong within a few seconds means reconnect) is the follow-up, below.

### Web client liveness (2.5 follow-up)

- **TCP doesn't tell you a peer froze.** A paused process keeps its sockets open: the kernel still ACKs, nothing sends a FIN, and the browser's WebSocket stays `OPEN`. Only the application can notice, by expecting traffic. The client pings every 5 s, and any server message within 5 s of a ping proves the server alive; silence means the socket is dead. Measured with a 30-second `docker pause`: players moved to the other server 8–10 s after the freeze instead of waiting 30 s for the zombie to wake up.
- **Timeouts that can only be late, never early.** The deadline starts when a ping actually goes out, not from "the last time we heard anything". Browsers throttle timers in background tabs, so a ping can leave late. Measured from the send, a throttled timer can delay a verdict but never declare a healthy server dead. Later pings don't reset a running deadline, or a dead server would be given more time with every ping.
- **Abandon, don't close.** On a dead link the WebSocket closing handshake never completes, so waiting for `onclose` could take minutes. The client bumps a generation counter (every callback from an older socket is ignored), calls `close()` and moves straight into the normal retry: backoff, a new single-use ticket from the lobby, then `hello {last_seq}` and a replay. The handshake gets its own 10-second deadline, because in the first seconds after a freeze the lobby still hands out the frozen server's URL, and that connection hangs instead of failing.
- **Jitter even for "reconnect now".** `room_moved` used to reconnect immediately. But a zombie that wakes up fences all its rooms in the same instant, and every player would hit the lobby in the same millisecond, a self-inflicted thundering herd. It now goes through the same jittered backoff (250–500 ms on the first try). Resyncing after a missed `seq` stays immediate, because only one client is involved.
- **The trade-off: false positives.** Any pong slower than 5 s, for example on a bad mobile link, costs a needless reconnect: a new ticket, a replay, and other players briefly see a leave and a rejoin. Rejected: pinging faster only during a match, because the connection would need to know the game's phase to save one tiny frame every 5 s. Rejected: relying on the server's 60-second idle close, which is far too slow for a round that lasts 80 seconds.

### 2.6b Weekly leaderboard

- **An idempotent consumer when the write itself isn't idempotent.** Kafka delivers at least once, and `ZINCRBY` adds again on every redelivery. So one Lua script first does `SET NX lobby:lb:seen:{match_id}` and only if that is new increments each player's score. Because both steps run in one script, a crash can't leave a match marked but not counted (lost) or counted but not marked (counted twice), and two deliveries at the same moment can't both pass the check (a test fires 20 at once; exactly one applies). Rejected: two separate commands, which lose or double-count on a crash between them. The dedupe key is the natural key, `match_id`, so it covers both a producer retry and a consumer redelivery. How it fails: the marker lives 8 days, so replaying the topic from further back (an offset reset) would count old matches again; and in Redis Cluster the two keys hash to different slots, so the script would need a redesign there.
- **Retry a transient failure, skip a deterministic one.** Offsets are committed by hand, only after the script ran, and no rebalance happens between a poll and its commit (`BlockRebalanceOnPoll`). If Redis is down, the consumer retries with backoff and never moves past the match: the leaderboard stalls (consumer lag grows, which the ConsumerLagGrowing alert covers) but is never wrong. A record that can never succeed, an unknown `oneof` case from a newer producer, an empty wrapper or bytes that don't decode, is logged with topic, partition and offset, counted as `skipped` and committed (ADR 0004), so one poison message can't block a partition forever. Rejected: auto-commit, which commits on a timer regardless of whether the write happened, so a crash loses matches.
- **Event time, not processing time.** A match counts towards the ISO week of its `ended_at` in UTC, so a consumer that is hours behind still files a Sunday-night match under Sunday's week. Tests pin the boundary: Sunday 23:59:59 and Monday 00:00 UTC land in different weeks, and 01:00 Monday at UTC+2 is still Sunday. The trade-off is that one global week flips at Monday 09:00 for a player in Tokyo; per-timezone boards would multiply the keys.
- **Names without a contract change.** `MatchFinished` carries only user ids. Options were adding names to the event (a contract change for display data), calling auth for every read (synchronous coupling on a read path), or caching. The lobby already sees each player's name in their access token on every join, so it keeps `lobby:names`. How it fails: a name is as old as the player's last join, and a player who never joined through this lobby shows as "Player <id>".
- **Ranks people expect.** Ranks use competition ranking (1, 2, 2, 4), and the caller's own rank comes back even when they are below the list: one more than the number of players with strictly more points (`ZCOUNT (score +inf`). The reads aren't one atomic snapshot, which is fine: the design doc already calls the leaderboard eventually consistent. Each apply runs in a `lobby.leaderboard.apply` span that kotel parents on the record's `traceparent`, so a match's trace runs from the game server's round end through Kafka into the lobby's Redis write.

### Lobby cold-start allocation (2.6b follow-up)

- **The symptom pointed at the wrong layer.** A freshly restarted lobby answered quick play with 503 for several seconds, and its logs blamed both game servers with `DeadlineExceeded`. The game servers' logs showed that the requests never arrived: the time was spent inside the lobby's gRPC client before the first byte was sent. Comparing both sides' logs for the same room id ruled out the servers in one step.
- **A DNS lookup nobody asked for.** `grpc.NewClient` resolves names with gRPC's DNS resolver, which by default also looks up a `_grpc_config.<host>` TXT record (a service config) and only reports addresses after both lookups. Docker's embedded DNS knows the A record but forwards the TXT query upstream, where a cold cache took 5–8 s (Go's resolver times out after 5 s and retries). Every first call waits for it, so the 2-second deadline ran out on each server in turn. We use no service config, so the fix is one dial option: `WithDisableServiceConfig`.
- **Reproduce the cold case on purpose.** Once the upstream cached the "no such name" answer, the bug vanished, which is why it only showed up after restarts. A probe on the stack network, using a fresh network alias per run so nothing was cached, made it repeatable: 5 of 6 runs needed 5.5–8.0 s before the first call succeeded, and with the option set, 6 of 6 succeeded in 4–8 ms. The unit test does the same in-process: a fake DNS server answers A at once and never answers TXT.
- **Defaults are decisions too.** gRPC's resolver default suits Google-style DNS-published service configs, not a Compose or ECS network. The same pattern sits in the game server's heartbeat client, which explains part of the 4-second first heartbeat recorded in task 2.1's evidence: it took 6–8 s in 4 of 10 cold starts, and it's fixed the same way (next section).

### Game-server heartbeat cold start (lobby fix follow-up)

- **One root cause, two clients.** After the lobby's `AllocateRoom` client was fixed, the same `grpc.NewClient` defaults sat in the game server's heartbeat client. Fixing one call site and grepping for the pattern is cheaper than waiting for the second incident.
- **Measure the cold case, not the average.** Before the fix, 6 of 10 cold starts registered in about 0.3 s and 4 of 10 took 6–8 s: every beat had a 1-second deadline and failed until the TXT lookup ended. An average of these numbers hides the bimodal shape; the tail is what an operator sees after a deploy. After: 10 of 10 in 3–18 ms.
- **Isolate the measurement from the shared stack.** Other work was running on the local stack, and the upstream DNS caches the "no such name" answer after one lookup, so restarting the real game servers would have disturbed others and been warm after the first try. Instead, the real image ran next to a stub lobby under a fresh network alias per run: cold every time, and nothing shared was restarted.
- **Make the helper testable.** The dial options moved from `main` into `heartbeat.Dial`, so a unit test can point them at a fake DNS server that never answers TXT queries (a `dns://` target) and assert that the first heartbeat still succeeds.

### 2.6a Shared canvas

- **Pairing is a rule over the draw order, not a new data model.** A round's drawer became a list. From four present players (counting the 15-second takeover grace), the next two who haven't drawn share the canvas; each player still draws once per match, so 5 players play 2, 2, 1. The proto already had `drawer_ids` and `DrawerIDs`, so the contract didn't change: designing it as a list in task 2.2 paid off here.
- **Who chooses, and what happens when they leave.** Only the first drawer gets the options. If they leave while choosing, the options pass to the second drawer and `choosing` is sent again. The one who left stays a drawer, because they saw the options: as a guesser they would know the answer is one of three words. One drawer leaving no longer ends the round; both leaving does.
- **An automated review caught a stall.** My first version gave the new chooser the full 10 seconds. Two players leaving and rejoining in turn could then keep a round in choosing forever. The fix keeps the original deadline, and a test passes the choice back and forth 20 times and checks the timer still fires. The rejected alternative, one hand-over per round with a fresh timer, is fairer to the second drawer but adds state for a rare case.
- **Changing a stored format without breaking stored rooms.** The Redis snapshot replaced `drawer` with `drawers`. A room written by an older server still restores, as `[drawer]`, and a test feeds the new code an old-shaped snapshot. Rolling back is not safe the other way round: an older server ignores `drawers`, so in a pair round it would treat the second drawer as a guesser who knows the word. Deploys must not mix versions while pair rounds run, or the snapshot needs a version field.
- **Identity is (user, stroke id), everywhere.** Two drawers can both send `s1`. Undo, the client's state, the canvas painter's per-stroke "last point" and the local overlay all key strokes by user plus id, and the tests use colliding ids on purpose. Server-side, undo was already own-strokes-only; the property test now runs up to 6 players, so random walks cover pair rounds, undos across drawers and hand-overs.

### M2 Full match with five web clients

- **Testing multiplayer without five Google accounts.** Sign-in goes through Google and the web app keeps the access token only in memory, so extra browser tabs share one refresh cookie and are the same user. The extra seats ran the web app's own client code (`RoomConnection`, the reducer, the stroke batcher) in Node 24, with access tokens minted by auth's `TokenIssuer` and the local dev key. The game server checks those tokens the same way as real ones, so nothing about auth was faked on the server side.
- **Why that still counts as end to end.** The Node seats run the same code as the browser, from the same files, through the gateway, the lobby's join tickets and the same game servers. Only the drawing on screen is missing, and the one real browser covered that. The trade-off: only one window was checked by eye, so the other seats were checked from their state instead (the same results and the same event order in every seat).
- **Checking the server, not just the screen.** The browser showed the labels and scores, and Kafka confirmed the rest: three `RoundFinished` with the undone stroke left out of `strokeCount`, and one `MatchFinished` with a shared 2nd place.

### Review hardening (after M2)

- **Secrets leak through traces, not just logs.** The gateway's access log already dropped query strings, but the OAuth callback's authorization code and state were still in Tempo twice: as `url.query` on auth's span and as `http.target` on the gateway's. Auth now redacts every query value (names stay), so there is no list of sensitive parameters to keep up to date, and the gateway doesn't trace that one route. A test sends a known fake code through the real OTLP export path and checks that no attribute of any span contains it.
- **Fencing has to cover every write, including the small ones.** Event appends, snapshots, renewals and closes compared the lease with `<server_id>:<token>`, but ticket redemption only checked the server id. The risk was small (used-ticket markers, not room state), but "every write is fenced" is only worth saying if it's true. A room now carries the token it was taken with, and the redemption compares the exact lease value. A test shows the old prefix check accepts an older and a newer token, and the new one doesn't.
- **Refuse, don't strip, when the tool can't do "all".** nginx can clear named headers but can't match them by pattern, so "strip every `X-User-*`" was really three names. A six-line njs function (the module already ships in the official image) flags any `X-User-*` or `X-Roles` header, and the gateway answers 400. Rejecting fails closed and is easy to test with curl; silently dropping would hide a misbehaving client.
- **An audit is worth doing against your own docs.** Each of these was a place where the docs claimed more than the code did. Comparing the two found them, and running the M2 tests repeatedly (`-count=10`) also found a test that only passed on its first run in a process.

### Review fixes (after M2)

- **Connected isn't the same as seated.** Quick play compared connected players with `max_players`, but a player who steps away keeps their seat for the rejoin grace, so the lobby could send someone to a full room. The fix reports what the game server actually enforces (`len(players)`) as an additive proto field, `RoomStatus.seats`; an older server sends 0 and the lobby falls back to the connected count, so the rollout needs no ordering.
- **Every request deserves an answer.** A resume with nothing missed, from a socket the server still counted as open, got no message at all, and the client's handshake timer abandoned a working connection. Now every resume ends with `resumed {seq}`. That also gives the client something to check: if the server's seq is ahead of what it applied, events went missing and it resyncs.
- **Ask the source of truth, not the cache.** `AllocateRoom` answered "already running" from the server's in-memory map, even when the room had just lost its lease and was about to close. It now checks the lease in Redis first, stops the stale copy (waiting with the lock released) and takes the room again with a new fencing token.
- **Single-flight has a scope.** The refresh was single-flight per tab, but the refresh cookie is per origin, so two tabs refreshing at once looked like token theft and logged the user out. A Web Lock makes the critical section match the shared resource. The same theme: a zero score still created a leaderboard entry, because `ZINCRBY key 0 member` creates the member.
- **Tests should prove the claim in the roadmap.** The takeover-resume test resumed every client from its latest seq, so nothing was replayed, and the word-leak test's "reconnect" was really a fresh welcome. Both now go through a real replay. Each new behaviour test was checked against the old code (mutation spot checks), so it fails without the fix.

### Secret scanning (before making the repo public)

- **Scan history, not the working tree.** Deleting a secret in a later commit doesn't remove it from history, and going public publishes every commit, branch, PR and Actions log at once. gitleaks scans every commit (CI checks out with `fetch-depth: 0`). A scan of all branches found 13 hits, all JWT test fixtures; separate searches for private-key headers, Google client secrets, Stripe and AWS keys found nothing.
- **Allowlist by reasoning, not by noise.** The fixture tokens are safe because their signing key is generated per run and never written down, so nobody can sign new tokens with it. The exception is scoped to one rule and one file, and a planted token in any other file is still caught (checked in a scratch repo).
- **Verify your security config fails when it should.** The first config used a top-level `[[allowlists]]` with `targetRules`; gitleaks 8.28 loaded it and silently ignored it when extending the default rules. A positive run and a negative run (a planted leak elsewhere) showed the per-rule form was the one that actually works.
- **Some checks shouldn't be path-filtered.** Service workflows run only when their files change, but a secret can land anywhere, so `secrets.yml` runs on every PR. It always reports a status, which also makes it usable as a required check once `master` has branch protection.

### Durable outbox (ADR 0009, before task 4.4)

- **The transactional outbox, inside a Lua script.** The game server has no database, but it already commits each actor step to Redis in one fenced script. Writing the finished round into `room:{id}:outbox` in that same call makes the event durable exactly when players see the round end, and only by the lease holder: a fenced owner can't write an event for a round the next owner will replay with a different result. The same hash tag keeps it Cluster-safe.
- **Why not one global stream with a consumer group?** `XAUTOCLAIM` would give recovery for free, but the global key is in another slot, so it can't be in the fenced script. Written right after the commit, it is a dual write again: a crash in between loses the event. The per-room design reuses the takeover the system already has for recovery instead.
- **At-least-once, end to end.** The `event_id` is fixed when the entry is written, so a resend after a crash, a timeout or a takeover carries the same id, and consumers dedupe by it (or by `match_id`). The entry is deleted only after Kafka confirms; the delete isn't fenced, because a late delete by an old owner removes an event both owners publish identically.
- **Measured on the local stack:** Kafka stopped, a 4-player match played (3 entries in the outbox), the owning game server killed. The other server took the room 6 s later and queued all 3; Kafka was started again and all three events were in Kafka 7 s later with the outbox's event ids, and the room closed once its outbox was empty. Before, those three events would have died with the killed process.

## Stage 3: Drawing lifecycle

### 3.1 Assets skeleton

- **One conditional UPDATE is the whole concurrency story.** Every status change is `UPDATE ... WHERE id = ? AND status IN (allowed)`, and the caller looks at the row count. Under READ COMMITTED, a second writer waits for the first to commit, then re-checks its WHERE clause against the new row, so of eight moderators clicking at once exactly one wins (a test proves it with eight connections and a barrier). No `SELECT ... FOR UPDATE`, no read-then-write window. The same call makes a redelivered Celery task a no-op.
- **Who may decide from where is part of the state machine.** The AI decides only from `processing`, and a moderator only from `review`. Once a drawing has gone to the queue, a late AI answer (a retry that timed out but actually succeeded) can't overrule it. Check constraints back it up: a decided drawing always says who decided and when, so a buggy code path fails loudly in Postgres.
- **UUIDv7 over UUIDv4 or a deterministic id.** v7 is still random enough that ids can't be guessed, but time-ordered, so inserts append to the B-tree instead of splitting random pages, and the gallery can page by id. A UUIDv5 of `(match_id, round_no)` would make replays map to the same id for free, but the `UNIQUE(match_id, round_no)` constraint already gives idempotency, and derivable ids leak structure.
- **At-least-once tasks, on purpose.** `acks_late` plus `reject_on_worker_lost` plus prefetch 1 means a task whose worker dies is redelivered rather than lost; the price is that every task must be idempotent. There is no result backend, because the drawing's state lives in Postgres, and Redis' `visibility_timeout` must exceed the longest task and retry countdown, or the broker delivers it twice.
- **Bridging an SPA's token into a server-rendered admin.** The browser can't attach a bearer token to a navigation, so the web app calls `POST /admin/sso/` once with the token in the `Authorization` header and gets a one-hour, `/admin/`-scoped, HttpOnly session. CSRF stays on: `GET /admin/sso/` hands out the token (another origin can't read it). The first live run failed: nginx forwards `Host` without the port, so Django's Origin check refused `http://localhost:8080`. The fix trusts the public origin explicitly instead of rewriting `Host` for every service.

### 3.2 Pipeline

- **Where the dedupe happens.** Kafka and the game server's outbox both deliver at least once, and Celery does too. Each layer has its own idempotency. A unique `(match_id, round_no)` turns a replayed `RoundFinished` into a lookup. The task skips every step whose result is already on the row. The objects are content-addressed, so uploading again changes nothing. The consumer commits the offset only after the row and the task exist; a crash in between replays the record, and the replay just sends the task again.
- **Poison pills.** The first version retried any `DatabaseError`, which includes `DataError`: one record with a too-long id would have been retried forever and blocked its partition (an automated review caught it, and a test proved the stall against the old code). Now only connection errors are retried, records are validated against the column sizes, and anything the database still refuses is skipped, counted and committed. Retry what time can fix, never what it can't.
- **Claim check, then a copy.** The event carries only the stroke log's key, keeping Kafka messages small. The bucket copy expires after 7 days, so the first step copies it into a versioned MongoDB document and renders from that from then on. A drawing whose log is gone becomes `failed` (terminal, with a reason) instead of retrying forever or landing in the review queue without an image.
- **Content addressing needs deterministic bytes.** "Identical images are stored once" only works if the same strokes always render to the same PNG: no timestamps or metadata, fixed compression, a pinned Pillow. In the live data, 67 drawings share 15 images. The hash is of the rendered output, so changing the renderer gives new keys; old objects stay valid, and nothing has to migrate.
- **Recovery is a sweep, not a hope.** Celery's retries cover a short outage (5 attempts, exponential backoff with full jitter). A message Redis lost, or retries that ran out, are covered by a beat task that re-queues drawings untouched for 10 minutes. It uses `SELECT ... FOR UPDATE SKIP LOCKED`, so even two sweepers never take the same row, the same pattern as the game server's stale outbox re-queue.

### 3.3 Moderation

- **Sort failures by whether time can fix them.** A timeout, a connection error, 429 or 5xx means "ask again later", so it retries with exponential backoff and full jitter: drawings that failed together during an outage don't retry together. A 4xx or an unreadable answer means "this request is wrong", so retrying only burns budget; it goes straight to a human. The same rule fixed 3.2's poison-pill bug.
- **The retry budget lives on the row, not in Celery.** `moderation_attempts` is incremented before each call, so the 4-call budget holds across task redeliveries, worker crashes and sweeper re-queues. Celery's own retry counter resets whenever the task is sent again. After the last failure the drawing goes to the review queue with the reason, which is the graceful degradation: an AI outage slows moderation down, it never loses or auto-approves a drawing.
- **Three answers, not two.** Real moderation routes low-confidence cases to people. The stub's `review` decision exercises that path now, so a Stage 7 model can plug in without a contract change. The guarded `decide` from 3.1 means a late AI answer can't overrule a drawing that's already in the queue.
- **A timeout doesn't cancel the work.** In the slow drill, each client gave up after 3 s while the stub kept working for 5 s, so a slow dependency keeps burning its own capacity on answers nobody reads. A real service would pass a deadline along (like gRPC deadlines) or cancel on disconnect; the rejected alternative was a circuit breaker, which adds state to save load during long outages.
- **Operator switches belong on a port nobody routes.** The stub's mode changes at runtime through `/internal/moderation-mode`, which answers only on port 9091. The same uvicorn server listens on two sockets, and the route checks which one a request came in on. The gateway proxies the service port only, and a live `PUT` through it got 404. Inside the network anyone can still reach it, which is the same trust boundary ADR 0006 accepts for gRPC.

### 3.4 Events and API

- **The dual-write problem, solved the boring way.** Updating Postgres and then producing to Kafka can leave one without the other after a crash. `decide()` writes the event into an outbox table in the same transaction as the status change; a separate relay publishes it. A test makes the outbox insert fail and checks that the decision rolled back with it. It's the same idea as the game server's Redis outbox (ADR 0009), with Postgres's transaction instead of a Lua script.
- **At-least-once from the relay, and why it's fine.** The relay stamps `published_at` only after Kafka acknowledges, so a crash between the ack and the stamp republishes the same `event_id` (a test kills it there and finds the event twice in Kafka). The producer is idempotent, so its own retries never duplicate; only the relay's crash can, and the marketplace dedupes with `ON CONFLICT DO NOTHING`. The rejected alternative was Kafka transactions, which can't include the Postgres write.
- **SKIP LOCKED for a work queue in Postgres.** Two relays (or two sweepers) each lock a batch with `FOR UPDATE SKIP LOCKED`, so they never take the same row and never wait on each other; a test runs two relays over 40 events and counts exactly 40 messages. Rows of one drawing share a Kafka key, so they stay in order on one partition.
- **Presigned URLs keep bytes off the app servers.** The API hands out 15-minute GET URLs signed with SigV4, so images go from storage to the browser, which is how S3 works in AWS. The signature covers the host, so the URL must be signed for the address the browser uses (`localhost:8333`), not the internal one. The live check caught exactly that: the setting had landed in the wrong compose anchor.
- **404, not 403, for what you can't see.** A drawing that isn't approved exists only for its authors; everyone else gets the same 404 as for an id that never existed, so ids leak nothing. Pagination is keyset on the UUIDv7 primary key (`WHERE id < cursor ORDER BY id DESC`), with a partial index on approved drawings, so page 1,000 costs the same as page 1.

### 3.5 Web gallery

- **Reconstructing time from what the server recorded.** The log has each stroke's `server_received_ms` (when the last batch arrived, by the server's clock) and per-point `t_ms` (client clock, since the stroke began). So a stroke starts at receive time minus its duration, and its points land at their offsets from there. Server time orders and spaces the strokes, so two drawers interleave correctly; client time only paces points within a stroke, which matches the rule that client clocks never decide anything. A fast client clock can't place a stroke before the round, because the start is clamped at 0.
- **What the data can't tell you, don't fake.** The log records that a stroke was undone, not when, so the replay leaves undone strokes out rather than invent an undo moment, and it ends on exactly the image that was moderated and minted. Long pauses are squeezed to one second and the leading wait is dropped, a choice about the viewer's experience that doesn't change the order of anything.
- **The timeline is a pure function; only the painter touches the canvas.** `timeline(replay)` returns sorted events, `eventsUntil` is a binary search, and the painter draws only the new segments (repainting only when the replay goes back). That made the timing logic testable without a canvas, and the player testable with fake timers (1x, 4x, pause, replay from the end).
- **One origin is a security property.** Checking a branch on a second dev server, auth refused the refresh because the Origin was `localhost:5174`, which is the CSRF defence doing its job. The local proxy presents the gateway's origin instead; in production there is only the gateway. Presigned URLs keep image bytes off the app entirely, so the gallery's cost is one small JSON request per page.

### Stage 3 review fixes

- **Health checks must test what the dependants need.** Mongo's check pinged localhost, and on a new volume the image's temporary init server answers there about 2 s before the real server accepts other containers, so `mongo-users` sometimes got `ECONNREFUSED`, and it failed CI once. The check now goes through the container's network address, and the job retries anyway. Same lesson as the test fixture in 3.2: "up" isn't "ready for me".
- **Telemetry identity is per process, not per container.** gunicorn's workers and Celery's pool processes each export their own cumulative counters, and under one `service.instance.id` Prometheus saw one series that reset hundreds of times, so every `rate()` was wrong. A per-process suffix fixed it. The check that found it was simple: `resets()` should be 0 on a counter that never restarts.
- **A test client that skips a check proves nothing about it.** Django's test client turns CSRF off, so "POST gives 405" passed while real requests got a 403 CSRF page. The API now declares what it is: token-authenticated with no cookies, so it's CSRF-exempt, with JSON errors for every status. Its test uses a CSRF-enforcing client.
- **Count what you can observe, not two overlapping numbers.** The relay added librdkafka's `flush()` remainder (which includes internal requests) to the failed delivery reports. The fix counts the batch minus what Kafka confirmed. It made a flaky test (2 in 5) deterministic and the failure metric honest.
- **Close the loop in CI.** The stack job only checked health endpoints, so nothing in CI ever ran a round through the pipeline, and the runner's small disk (the SeaweedFS volume bug) went unseen there. `make pipeline-check` now sends one `RoundFinished` and waits for the approved, stored, published drawing.

## Stage 4: Economy

### Task 4.1: Ledger core

- **The database guards the money, not just the code.** The service checks that postings balance, but Postgres checks again: a deferred constraint trigger sums each transaction's entries at `COMMIT` (entries arrive one by one, so only the finished set has to balance), triggers refuse `UPDATE`/`DELETE`/`TRUNCATE` on the ledger, and a plain `CHECK` refuses a negative user balance. That `CHECK` needs to know whether the account is a user's, so `balances` carries a copy of `owner_type`, pinned to `accounts` by a composite foreign key so it can't drift. A trigger instead of `REVOKE` because the service's user owns the tables and could grant itself the rights back. Rejected: app checks only, which leaves a hand-written `psql` statement or a buggy later migration one step from a broken ledger.
- **Deadlocks are prevented by lock order, and the test proves it both ways.** Every posting locks all its balance rows in one `SELECT ... ORDER BY account_id FOR UPDATE`; Postgres sorts before it locks, so two opposite transfers queue instead of each holding one row and waiting for the other. 800 opposite transfers on 8 threads finish with no deadlock; a mutation that locks one row at a time in request order fails the same test with `deadlock detected`, and a second test reproduces the deadlock deterministically with two raw connections (Postgres needs its 1 s `deadlock_timeout` to notice).
- **Idempotency is a UNIQUE constraint, not a lookup.** `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING tx_id`: no row back means a replay, so the call returns the first `tx_id` and writes nothing. Two concurrent calls with the same key can't both win: the second waits on the unique index until the first commits (then sees its row) or rolls back (then goes ahead). A "check then insert" would let both pass the check. 20 threads, one key: one transaction.
- **Reconciliation reads one snapshot and can't lie with a 0.** The job runs its two queries in one REPEATABLE READ, read-only transaction, so a posting that commits between them can't create a false mismatch, and it takes no locks, so postings never wait for it. Its gauges stop reporting when no run has succeeded for 3 minutes: a dead job shows as a missing series (its own alert), not as "0 problems". Live, a balance edited by one coin showed up in Prometheus 9 seconds later.
- **How it fails.** Coins can't be lost or double-spent, but the job is a full scan every minute, fine for thousands of entries and too slow for hundreds of millions (Stage 6 brings monthly partitions and incremental checkpoints). The deferred trigger is O(n²) per transaction, fine for the 2–5 entries a purchase has. Without the agent the gauges are no-ops, so tests check the job's result object, not the exported metric.

### Task 4.2: Ownership

- **Idempotency by natural key, not by event id.** A redelivered `DrawingApproved` (the assets relay is at least once) must not mint twice. The drawing id is the ownership row's primary key, so `INSERT ... ON CONFLICT (drawing_id) DO NOTHING RETURNING` is the whole dedupe: no row back means "already minted", and the authors and the `MINT` event are only written by the transaction that created the row. A separate processed-events table would be a second thing to keep in sync. Live, replaying the whole topic changed nothing.
- **Commit the offset after the database, and decide what may be skipped.** The listener acknowledges a record only after the mint committed, so a crash in between means a redelivery, which is a duplicate. A record that can never succeed (undecodable, an unknown event from a newer producer, an event that breaks its contract, a value Postgres refuses) is logged, counted and committed so it can't block the partition. Everything else, a Postgres outage above all, is retried on the same offset with no limit: an approved drawing is never skipped, and the cost is lag, which has its own alert. A test pauses the Postgres container and watches the record retried and minted afterwards.
- **A gotcha worth telling: the consumer group.** Spring Kafka uses a `@KafkaListener`'s `id` as its group id unless told otherwise, so the first build joined group `drawing-events` instead of `marketplace`. The test logs showed it; `idIsGroup = false` fixed it. Renaming a group silently restarts consumption from `auto.offset.reset`, which is why it matters.
- **Reconciling ownership means checking agreement, not existence.** The primary key already guarantees at most one ownership row, so "exactly one owner" is trivially true. What can go wrong is a sale that updates one table and not the other, so the job checks that every drawing has one `MINT`, a `version` equal to its number of ownership events, an owner equal to the latest event's new owner, and authors. Live, an owner edited by hand showed up within one run.
- **How it fails.** If assets publishes a bad `DrawingApproved` (owner not the first author), the drawing is never minted and only a counter and an error log say so; there is no dead-letter topic yet. A long Postgres outage stalls minting for its whole length. Co-drawn royalties are still open (before 4.6), but every author is recorded in order, so either answer fits.

### Task 4.3: Listings and purchase

- **One transaction, one lock order.** A purchase locks the listing, then the drawing's ownership row, then the balances in account order, and moves coins, the listing, ownership and the `SaleCompleted` outbox row together. Concurrent buyers queue on the listing's `FOR UPDATE`; the first sells it and the rest find it `SOLD` and get 409 without a coin moving. The test: 50 buyers at once, one owner, 49 × 409, ledger at zero, in a quarter of a second.
- **Defence in depth shows up in an experiment.** With the listing lock removed, the race still ended with one owner: the ledger posting uses the key `sale:<listing_id>`, so the second payment for one listing waits on that unique index and fails. The answers were wrong (500 instead of 409), but no money moved twice. Two independent guards on the same invariant.
- **Idempotency keys as a lease with a fencing token** (ADR 0012). The key is claimed in its own transaction with a 30-second lease and a random token, and completed by the work's transaction with an update that matches only that token. A crashed request's key frees itself; if a slow original finishes after a retry took the key over, its completion matches nothing and its whole transaction rolls back. It is the game server's lease-and-fence idea (ADR 0007) applied to a request. The rejected option (the key inside the work's transaction) is simpler but can't wrap the Stripe call in 4.5.
- **Remember the answer, not just success.** A lost race (409) or insufficient funds (422) is stored and replayed like a 200, byte for byte from a `TEXT` column (JSONB reformats it), so the same key always means the same outcome. A first version of the fencing test took 30 seconds: both requests paid from the rewards system account, and the slow one held its balance row. That is a real hot spot for 4.4's rewards.
- **The outbox, honestly at least once.** The relay locks rows `FOR UPDATE SKIP LOCKED`, sends, and marks only acknowledged rows. With the broker paused, a send that the relay had given up on still arrived later, and the next pass sent it again: two copies with one `event_id`. That is why every consumer dedupes. Live, Kafka stopped for 50 s didn't stop a listing; the lag gauge rose to 42 s and drained 5 s after Kafka came back.

### Task 4.4: Rewards

- **The natural key is the dedupe.** The game server's outbox delivers `MatchFinished` at least once with a fixed `event_id`, but the marketplace dedupes on the match itself: one ledger transaction per match with the idempotency key `reward:<match_id>`. On the local topic, 3 of 55 records were the same match delivered again, and they paid nothing; resetting the consumer group and replaying all 56 changed not one coin.
- **One transaction per match, not per player.** The design doc first said one key per player. One per match pays a match all or nothing and locks the `rewards_issuance` balance row once instead of once per player. That row is a hot spot: every reward and every Stripe credit locks it, which a 4.3 test had already shown when two requests waited 30 s on it. The cost: one bad player id refuses the whole match (counted and logged).
- **The same event, many consumers, one trace.** `MatchFinished` is read in parallel by the lobby (leaderboard) and the marketplace (coins), each in its own consumer group, and the trace shows both under the game server's `game.match.end`. The reward committed about 60 ms after the match ended, and its `CoinsCredited` events went out through the outbox under the same trace.
- **A security review made the contract stricter.** Kafka doesn't authenticate producers yet, so anything on the internal network could publish a `MatchFinished` and mint coins. Broker ACLs are infrastructure work for later; a cheap bound now: a room holds at most 8 players, so more results than that is refused as a contract violation.
- **How it fails, and a rule to revisit.** A forged but well-formed match still pays up to 8 × 30 coins until Kafka has ACLs. And the data showed a farming gap: when nobody scores, everyone ties for first and gets 30. A rule such as "a score of 0 earns only the participation reward" would close it; it's Bowen's call.

### Task 4.5: Stripe coin packs

- **Trust the signature, not the payload's numbers.** The webhook has no JWT; Stripe's `Stripe-Signature` header is an HMAC-SHA256 of the timestamp and the raw body with the endpoint's secret, and anything older than 5 minutes is refused, so a captured request can't be replayed later. Even then, the coins credited are the ones the marketplace recorded when it created the checkout session, not a number in the event: a session it didn't create, or whose metadata names someone else, is logged and not paid.
- **Two dedupe keys for two kinds of repeat.** Stripe redelivers events (at least once, and `stripe events resend` does it on demand): the event id in `stripe_events` catches that. Stripe can also send two different events about one payment (`completed`, then `async_payment_succeeded`): the ledger key `stripe:<session_id>` catches that. Both live in the same transaction as the credit.
- **Answer 2xx to everything you can't fix.** After a valid signature, every outcome (processed, duplicate, ignored, unknown session) is 2xx, because a non-2xx makes Stripe retry for days and retrying an unknown session can't help. Only a bad signature is 400.
- **Idempotency on the way out, too.** The checkout request takes an `Idempotency-Key` (ADR 0012's leased claim, the case that pattern was chosen for: the work calls an external API), and Stripe gets an idempotency key derived from it, so a double click or a retried request after a timeout gets the same Checkout Session instead of two.
- **Testing a payment provider without one.** CI runs Stripe's own `stripe-mock` image through Testcontainers, so the request the SDK builds is checked against Stripe's API definition, and signs webhook events with the SDK's own HMAC code. A real test-mode payment is still the last check, by hand, with the Stripe CLI forwarding webhooks. Small gotcha: stripe-java's models carry Gson annotations, so with `-Werror` the build needs Gson on the compile classpath.
- **The live payment failed safe first.** The first real test payment credited nothing: the Stripe CLI was logged into a different account than the sandbox key, so the event had no listener. The Stripe API showed the session paid with `pending_webhooks: 0`. The fix was operational (run the listener with the key's account), and the second payment credited exactly once; `stripe events resend` then came back `duplicate`. A payment system's first job is to not pay twice; its second is to make a missed event visible, which is why the next step would be reconciling paid Checkout Sessions against `stripe_checkouts`.

### Task 4.6: Royalties

- **One rule instead of special cases.** The first rule paid royalties only when the seller wasn't an author, which left the second drawer of a pair drawing with nothing when the first sold it. The rule now: the authors who are neither the seller nor the buyer share 10 %. It covers solo authors, co-authors selling, strangers reselling and a co-author buying back, with no branches for any of them.
- **Rounding that can't create or lose a coin.** `floor(price × 10 / 100)`, split in whole coins, the remainder to the first author in drawing order, and a share of 0 left out because the ledger refuses zero entries. A randomized test runs 20,000 sales and checks that the seller's amount plus the shares is exactly the price; a fixed table covers the edge cases, like 9 coins (no royalty) or 1,000,000 between 7 authors (14,290 + 6 × 14,285).
- **I got the arithmetic wrong in the plan; the test didn't.** I wrote "1,000,000 between 7 → 14,286 + 6 × 14,285" into the plan; that sums to 99,996. The test failed, and the correct remainder is 5. It's a good argument for property checks next to hand-written cases.
- **Royalties are just more ledger entries.** No new table and no second transaction: the shares are postings in the purchase's ledger transaction, so their balance rows join the sorted lock set, and the 50-buyer race test still passes with them.

### Task 4.7: Notifier and API keys

- **Webhooks only for your own account.** The design said "developers subscribe to event types" but not whose events; a public feed would have shown every player's trades and Stripe purchases to anyone with an API key. Each event now goes only to the endpoints of the users it involves (seller, buyer, royalty recipients; the credited user), a decision recorded in ADR 0014.
- **The queue is a table.** One row per (endpoint, event) is the work queue and the delivery log at once: a unique key makes a redelivered Kafka record a no-op, workers claim due rows with `FOR UPDATE SKIP LOCKED` and a 60-second lease (a crashed worker's row comes back), and each attempt is logged. A dead delivery is its own outbox for the dead-letter topic. Kafka delay topics or a Redis sorted set were the alternatives; both would have needed a table for the log anyway.
- **SSRF is about addresses at send time, not URLs at registration.** Registration rejects the obvious (http, credentials, internal IP literals), but the real check is in the dialer: resolve, refuse if any address is internal, then connect to the address that was checked, so a DNS name that changes after registration can't reach the metadata service. A security review found a subtle hole I had: Go's `netip.Prefix.Contains` is false for a zoned address like `fe80::1%eth0`, so the zone has to be stripped first. Redirects are never followed, because a redirect could point inside.
- **Secrets the server must read can't be hashed.** API keys are random, so auth stores only a SHA-256 of their secret part. Webhook signing secrets must be read back to sign, so they are AES-256-GCM encrypted with the endpoint id as associated data (a ciphertext moved to another endpoint doesn't open). Another review point: a stolen access token could mint a long-lived API key, so a replayed rotated refresh token (auth's theft signal) now revokes the user's keys too.
- **Full jitter, observed.** The failing endpoint's eight attempts came 1.5, 1.0, 3.0, 14.1, 29.6, 8.0 and 120.9 s apart: random within ceilings that double from 2 s, so recovering receivers aren't hit in waves. Every attempt is a span in one trace that starts at the marketplace's reward, three minutes earlier.

### ADR 0013: Kafka client authentication and topic ACLs

- **Why Kafka got authentication when gRPC didn't.** ADR 0006 left the internal gRPC open because a forger there costs availability. Kafka is different: since task 4.4 a `MatchFinished` pays coins and a `DrawingApproved` mints a drawing, so the topic is the proof that the game server or assets decided it. Same trust boundary, different blast radius, different answer.
- **The ACLs are the control; the mechanism only names the caller.** The event catalog's producer and consumer columns became the ACL table: one writer per topic, readers only on their own topics and groups, nobody but `admin` can create, delete or reconfigure. SCRAM per service was chosen because it is configuration in franz-go, confluent-kafka and Spring Kafka, and the same generated-password pattern as Postgres. Because principals are plain service names, swapping SCRAM for mTLS or MSK IAM later doesn't change a single ACL.
- **Consumer groups are an attack surface too.** Without group ACLs, anything that can reach the broker can join group `marketplace`, take partitions and commit past `MatchFinished` records, so rewards silently disappear. Forged events are the obvious threat; skipped events are the subtle one.
- **No signatures on events.** Once only the game server can write `game.matches.v1`, a signature adds nothing: anyone who could forge a signed event already holds the producer's own credentials and key. `EventMeta.producer` stays a self-asserted field for debugging. What ACLs can't check is content, so the marketplace keeps its plausibility checks against a buggy or compromised producer.

### Task 4.8: The economy in the web app

- **An idempotency key belongs to an action, not to a request.** The web app makes one key when the player presses Buy and keeps it while the outcome is unknown: a network error, `409 IN_PROGRESS` or a 5xx all mean "maybe it happened", and retrying with the same key can never buy twice. Any real answer (sold, not enough coins, success) ends the action, and the next press gets a new key, because the server would replay the old answer byte for byte. Listing at another price is another action: the same key with a different body is `422 IDEMPOTENCY_KEY_REUSED`.
- **The redirect isn't the payment.** Stripe sends the browser back to `/wallet?checkout=success` before or after its webhook reaches us, so the page treats the redirect as a hint: it polls the balance for 30 s and says the coins are late rather than pretending. The wallet is only ever credited by the verified webhook.
- **Three small backend changes instead of a fat client.** Thumbnails come from one `?ids=` lookup per page in assets (not one request per row, and the marketplace doesn't copy drawing data it doesn't own); "my drawings" comes from a marketplace endpoint that answers only `owner=me`, because a list of everything a player owns is more than the per-drawing history reveals; and the notifier accepts the session's token, so a player manages webhooks without making an API key first.
- **Keyset pagination needs a total order.** My drawings sorts by acquisition time, which isn't unique, so the cursor is `(updated_at, drawing_id)` and the query compares the pair; a test puts two drawings in the same microsecond across a page boundary. Postgres and Java order UUIDs differently (unsigned bytes versus signed longs), so the test asks Postgres which comes first.
- **Shown once means shown once.** API keys and webhook secrets appear only in the create response (`Cache-Control: no-store` for keys), and the page drops them from memory when the player presses Done; the lists show only a prefix. The live check found the other side of that: a receiver without the secret refuses the webhook, and the notifier keeps retrying until it gets one or gives up.

### Fix: a maximum age for the cached JWKS

- **A cache without a maximum age makes a revocation impossible.** The lobby, notifier and assets verifiers refetched auth's JWKS only on an unknown `kid`, so a key that auth withdrew, even after a leak, stayed trusted until every one of them restarted. Now the set is refreshed after 10 minutes, which bounds how long a withdrawn key works; refetching on an unknown `kid` stays, so a rotation still works at once.
- **Fail open for a while, then fail closed.** If auth can't be reached, the last good set keeps working, because a JWKS outage shouldn't log everyone out. But only for an hour: past that every token is refused, otherwise an attacker who can block the fetch keeps a stolen key alive forever. An hour costs almost nothing, since access tokens last 15 minutes and only auth issues new ones.
- **Stale-while-revalidate without a goroutine.** When the set goes stale, the request that gets the fetch lock (`TryLock`) refreshes it, and every other request keeps using the cached keys instead of queueing behind a fetch that can take until its 3-second timeout. A test holds the fetch open and checks 20 concurrent requests still finish, and mutation checks showed each new test fails when its rule is removed.
- **Fake clocks make time rules testable.** The cache reads time through an injected `now`, so tests step through "9 minutes: still trusted, 10: refreshed, 59: still served while auth is down, 60: refused" in milliseconds and without sleeps.
- **The bug was copied once already.** The notifier copied the lobby's verifier, bug included, and assets wrote the same design in Python. Fixing the copies was the small change; extracting a shared Go module is the real fix for drift between the Go services, and it is its own decision. Across languages, the shared test fixtures are what keeps them honest.
- **The same rule in two languages has different traps.** Python has `Lock.acquire(blocking=False)` where Go has `TryLock`, and a lock-free reader checks the age outside the lock, so keys and fetch time are one tuple replaced in one assignment: as two attributes, a reader could pair a new fetch time with the old keys and accept a just-removed key.

### Stage 4 review

- **A review against the exit criteria, not just the diff.** Every M4 criterion was traced to a named test or an evidence row, and the suites were rerun several times (the marketplace 3 times, the notifier 5 times with `-race`) to look for flakes. None failed. The real findings came from comparing code with the design doc: a cache that was claimed but never built, a consumer the catalog listed that didn't exist, and a dead-letter alert that would have paged us for other people's broken servers.
- **Check-then-insert needs a lock, even for a soft limit.** The 10-API-key cap counted, then inserted. Thirty concurrent creates made 15 keys. A transaction-scoped advisory lock per user (`pg_advisory_xact_lock`) fixed it, without a table-wide lock or a schema change, and the new test fails without it.
- **Metrics have commit semantics too.** `market.purchases{result=success}` was counted inside the purchase, before the idempotency completion and the commit, so a rolled-back sale still showed up. It's now counted in an after-commit callback. A dashboard that disagrees with the ledger is a bug.
- **Be kind to a dependency that is down.** Every service retried a failed JWKS fetch after one second, forever. They now back off from 1 s to 30 s. An auth outage costs auth one fetch per 30 seconds per process instead of one per second, and recovery is still quick.
- **Alert on what you own.** A webhook going `DEAD` almost always means a developer's server is down. Paging on the dead-letter count would hand our on-call to strangers, so test pings stay out of it entirely and the alerts watch our own delivery health instead.

### Task 4.R1: Checkout outside the database transaction

- **A network call inside a transaction borrows a connection for as long as the other side takes.** The checkout called Stripe inside the transaction that completes the `Idempotency-Key`, so each checkout held one of 10 pooled connections for up to about 10 seconds. A slow Stripe would have starved purchases and even the Stripe webhook. Now the claim commits, Stripe is called with nothing open, and one short transaction records the session and completes the key: the connection is held for about 7 ms, not 820.
- **Exactly once still comes from the fence, not from the transaction.** If the slow request loses its claim (past the lease) and the retry takes over, the slow request's completion matches nothing, so its record rolls back. One session is recorded, and the orphan was never shown to the browser, so it can't be paid.
- **Read the provider's idempotency rules, not just its API.** Stripe's API v1 replays a saved response for an idempotency key, a 500 included, for 24 hours. Deriving Stripe's key from ours alone would have made one Stripe hiccup fail every retry of that checkout for a day. Deriving it per claim keeps the Stripe client's own retries safe and lets a new attempt ask afresh.
- **Test doubles must behave like the real thing where it matters.** stripe-mock can't be slow and doesn't replay keys, so the tests use a small stub that saves responses per key like Stripe and can hold requests. Each test was run against the old code to make sure it fails.
- **Rejected:** a nested `REQUIRES_NEW` transaction, because the outer one still holds its connection; an async checkout through an outbox, because the browser needs the URL now; a semaphore around checkouts, because it limits the damage without fixing the cause.

### Task 4.R2: Webhooks revoked with the credentials

- **A theft response must cover every channel the thief could have opened.** Auth already revoked the session family and the API keys, but webhook endpoints, made with either, kept streaming the victim's sales and Stripe credits. Now the same transaction writes `CredentialsRevoked` to an outbox, a relay publishes it, and the notifier disables the user's endpoints about 0.14 s after the replay, measured in one trace across three services.
- **Stateless tokens need a watermark to be revoked.** The thief's access token stays a valid JWT for 15 minutes. The notifier keeps the newest revocation time per user and refuses any credential issued at or before it: a session by `iat`, an API key by `created_at` (because its cache trusts a key for 30 seconds). The same idea would revoke JWTs anywhere, at the cost of a lookup per request.
- **Three security reviews changed the design.**
  - Every replay of the old token re-ran the theft response, so anyone holding it could keep revoking the user's new keys. Now it runs once per family, under a `reuse_handled_at` marker.
  - A request could pass the watermark check, the revocation could land, and the request's insert could commit after it. Registration, enabling and revocation now share the owner's advisory lock, and the writers re-check under it.
  - The thief's token could still mint a brand-new API key in auth, newer than the watermark. So auth keeps its own watermark for key management, re-checked under the user's key lock (the same check-then-act race again, one service over).
  - Each fix has a test that fails without it. The lesson: a revocation is only as strong as the weakest path that can mint a new credential.
- **Pick consumer offsets per topic's meaning.** The webhook consumer starts at the newest offset, so a new endpoint doesn't receive history. A revocation published before the notifier first subscribed must still count, so revocations get their own group reading from the earliest offset. That's safe because handling is idempotent: an event not newer than the watermark changes nothing, so a replay never re-disables an endpoint the owner enabled again.
- **Rejected:** the notifier asking auth on every delivery (auth in the hot path, and an outage stalls webhooks); auth calling the notifier directly (a revocation lost while the notifier is down); deleting endpoints instead of disabling them (the owner loses the id and the delivery log).

## Stage 5: Production readiness

### Task 5.1: Dashboards and alerts

- **Alerts are code, reviewed like code.** The 17 rules, the Discord contact point, the routing policy and four dashboards are files in `infra/observability/`, provisioned into Grafana on every machine and in CI. A lint ties them together: every alert in the spec has exactly one rule, every rule a runbook and a dashboard panel, and every metric a panel queries is in the metric catalog. So renaming a metric fails the build instead of leaving a dashboard silently empty.
- **Alert on symptoms and broken invariants, and make silence loud.** LedgerImbalance pages when the ledger doesn't sum to zero or a balance drifts from its entries. A dead reconciliation job reports nothing rather than a reassuring 0, so ReconciliationStale asks for the missing series explicitly. The drill gives a drill account 1 coin its ledger doesn't explain: the alert fired in 90 s, the notification went out 30 s later, and it resolved 90 s after the fix, without touching the append-only ledger.
- **0/0 is a trap.** An error-rate rule over a quiet service divides zero by zero. Grafana's math step treats the resulting NaN as firing, so on the first load three idle services were "pending" with no errors at all. The fix filters by volume inside the PromQL (at least 20 requests in 5 minutes) so idle services have no series. A rule should be tested against an idle system, not only a broken one.
- **Measure lag where every client agrees: the broker.** Go, Python and Java consumers each report lag differently or not at all, so a separate `kafka-metrics` collector reads consumer-group offsets from Kafka for all seven groups. **Rejected:** editing otel-lgtm's bundled collector config (a vendor file to re-sync on every upgrade); a third-party Kafka exporter image (we prefer official images).
- **Test the paging path without the secret.** The Discord webhook URL is a secret, so CI doesn't have it. Without it, the contact point falls back to the existing `webhook-receiver` test service, which now keeps unsigned bodies, and the drill checks that the FIRING message arrived. The weak spot: a wrong Discord URL in production is only noticed by a human, so the setup doc ends with running the drill and looking at the channel.

### Task 5.2: AWS deployment

- **Pick the deployment shape by what it lets you demonstrate and what it costs per hour.** ECS on Fargate gives rolling deploys, health checks, per-service security groups and IAM roles, while the stateful stores run on one EC2 host with a real disk. Managed Kafka alone would cost about $1.20 an hour. The stack is created per session and destroyed after it, by two Terraform roots: one that outlives sessions (state, images, third-party secrets) and one that is thrown away.
- **Twelve-factor gaps show up the moment you leave Compose.** Fargate injects secrets only as environment variables, and the Go images have no shell, so signing keys became PEM text in variables. The game server only knew static S3 keys, so it now uses the SDK's default chain (the task role). The gateway hard-coded Docker's DNS and the compose hostnames. Each fix is small and tested locally first.
- **The first deploy finds what plans can't.** EC2 refused an apostrophe in a security group description. Cloud Map owns its private zone, so the data host had to become a Cloud Map instance. A game server registered as `game-server-1-1`, so every WebSocket got 404 from the very server that owned the room. An empty block AWS doesn't store made every plan replace every service's DNS entry. Each is now a commit with its reason.
- **Least privilege includes the metadata service.** An automated security review caught that an IMDS hop limit of 2 would let any container on the data host (Postgres, Kafka) fetch the instance role and read every secret. The hop limit stays at 1, and only Grafana, which needs CloudWatch, runs on the host network.
- **Rejected:** public subnets with a public IP per task (the NAT gateway is cheaper per hour than 15 IPv4 addresses, and tasks stay unreachable from outside); Secrets Manager ($0.40 per secret per month, versus free SSM parameters); exposing Grafana publicly (it's reached through a Session Manager port forward). The weak spot: the data host is a single point of failure, and a teardown deletes all data, which suits demos and not much else.

### Task 5.3: First measurements

- **Measure where players are, and know what each number includes.** The k6 script plays real four-player rooms through the gateway. It times a stroke from the drawer's socket to the other players' sockets, putting the send time in the `stroke_id`, so no protocol change is needed. It also times ping round trips, which skip the room entirely. Comparing the two tells the network apart from the server. The server's own broadcast metric stayed under 0.1 ms even while players waited seconds, because it stops timing when an event is queued, before the socket write. A metric that can't see saturation would never fire its alert.
- **Find the knee, and name it.** In AWS, a game server with 0.25 vCPU pinned its CPU at about 20 rooms. Stroke fan-out went from 24 ms (p95, 10 rooms) to seconds at 80 rooms, and CloudWatch's ECS CPU showed which task saturated. The laptop run looked fine at 80 rooms, because there the bottleneck was the laptop itself. Local numbers aren't capacity numbers.
- **Recovery time scaled with the number of rooms.** Locally, a killed server's room resumed in 8.3 s under load. In AWS, a stopped server's 41 rooms took 36 s to move. The lobby moves rooms one at a time, in passes with a 4-second deadline, and each takeover call to an overloaded server can take its full 2-second deadline. The fixes are clear: move rooms in parallel with a bound, and hand rooms over on a graceful stop (task 5.5).
- **A load generator has its own failure modes.** The first runs found script bugs, not server bugs:
  - the wrong player became host;
  - the "wrong" guesses were real words;
  - dropped sockets were never resumed, so a failover turned into a flood of new rooms;
  - after a takeover, one room ran two drawing loops at once.

  All the k6 players also come from one IP. After a failover, every rejoin hit the gateway's 20-requests-a-second per-address limit, which real users only meet behind a shared NAT. The script now resumes exactly like the web app does, and applies each room event once, by its room-wide `seq`.
- **Rejected:** a load generator inside the VPC for this first pass. It would remove the home network from the client numbers, but it needs more Terraform, and the server-side metrics plus CloudWatch already located the bottleneck. It's the right next step when the numbers must be clean.
- **Re-measure after fixing, with the same test.** Four follow-ups merged after 5.3 (parallel room moves, input and send lag, Grafana links, otel-lgtm's memory guards), so I reran the identical ramp and stop drill in AWS. The stop test now passes: 40 rooms moved in 3 passes, 17.8 s after the shutdown instead of 36.7 s. It's still over the 10-second target, because the one surviving server was saturated. The new input-lag metric pinned the bottleneck on the room actors' inboxes waiting for CPU, not on socket writes. SlowBroadcasts fired to Discord on exactly that lag. A before-and-after only means something if the test and the setup stay the same.

### Follow-up to 5.3: failover time that doesn't grow with the room count

- **Two queues, not one.** The lobby moved a dead server's rooms one at a time, but so did the game server: `AllocateRoom` held the server-wide room table lock across the Redis reads and the event replay. Parallel calls from the lobby alone would only have queued on that lock, and the wait would have eaten each call's 2-second deadline. So both ends changed: the game server now holds its lock only to claim the room id and to install the room.
- **Bound the parallelism per target.** A takeover replays 500 to 700 events, which is CPU work on the target. The first version sent 8 at once. On a game server capped at 0.25 CPU, all 8 missed their 2-second deadline together, 6 half-done takeovers were thrown away, and the server's lease keeper missed its own deadline. At most 2 calls per server (8 in all) moved 62 rooms in 3.5 s with no timeouts. It's the same reasoning as sizing a connection pool for one downstream service, not one global fan-out.
- **Stop starting, don't kill.** A pass now stops starting rooms after 4 s, but rooms already out finish and record their move. Before, the pass deadline could cancel a takeover the game server had already done, and the next pass did it again. The reassigner lock is re-taken before every call, so its 10-second TTL only has to outlast one call, not a whole pass.
- **Spread by the pass's own count.** Every room of a pass used to go to whichever server was least loaded when the pass began. Now each room goes to the server with the fewest rooms, counting the ones this pass already sent there, so a dead server's rooms spread over all the survivors. With more than one survivor, that matters more than any per-server limit.
- **Check the measuring tools too.** One uncapped run looked like a regression: the last room moved after 130 s. In fact otel-lgtm's collector and Tempo had died silently under the 80-room ramp, while the container still reported healthy. With a working collector, the same run moved 39 rooms in 0.5 s.

### Follow-up to 5.3: seeing a server fall behind

- **A latency metric is only as good as where it stops.** `game.broadcast.duration` ended when an event was queued to each socket. In AWS it read under 0.1 ms while pongs waited 9 s, so the SlowBroadcasts alert could never fire. The fix was to time the queues themselves: `game.ws.send_lag` (from `Send` until the socket write returns, recorded by the writer goroutine) and `game.room.input_lag` (from the reader handing a message to the room until the actor starts on it, stamped before the possibly blocking send, so time blocked on a full inbox counts).
- **Measure first, then trust the metric.** The first version had only send lag, and its threshold looked sensible. A local run with both game servers capped at 0.25 CPU (`docker update`), like AWS, showed send lag rising 300 times, to about 200 ms, while players waited 10 s or more. The rest was on the way in: each room processes its 256-deep inbox one step at a time, each with a Redis commit. A second capped run with input lag added found it: at 40 rooms its p95 was 1.8 to 2.4 s, within a few percent of k6's stroke fan-out, and SlowBroadcasts fired on `lag=input` 5 minutes later. Without the capped runs, the alert would have shipped blind again.
- **Cause and symptom, side by side.** The alert fires on what players feel (input or send lag p95, one alert instance per lag via `label_replace`). The Go runtime's own scheduler-latency histogram (`go.schedule.duration`, one producer added to the meter reader, no hot-path code) says why: above a few milliseconds the CPU is pinned; low means slow clients or slow Redis. It was the cleanest signal of all (about 1 ms healthy, 100 to 700 ms pinned), but a cause isn't what players feel.
- **Cheap enough to keep on.** One clock read and one histogram record per message per socket: about 110 ns on one core, 160 to 350 ns with 4 to 8 writers contending on the same series, no allocations (`BenchmarkSendLagRecord`). At 11,000 messages a second that is about 2 ms of CPU per second. There are no ids as attributes, so the series count stays fixed whatever the number of rooms.
- **Load tests find bugs in protection logic too.** Under the capped run, 485 sockets were closed with 1008 ("flooding"). They had sent nothing unusual: the server stalled, their messages piled up in the kernel, and the reader then took them in one burst over the flood limit. The server punished clients for its own stall. It's a separate fix, but only a saturated server shows it.

### Follow-up to 5.3: the telemetry stack that died under load

- **"Silent" deaths leave a record, one layer down.** Tempo and the collector vanished from otel-lgtm with nothing in the container's logs, and the container stayed healthy. The Docker VM's kernel log had the answer: global OOM kills, with no container memory limit, so the kernel picked the biggest process, Tempo at about 3 GiB, and once the collector at 2.4 GiB. When a process disappears without a word, check `dmesg` before reading application code.
- **Volume was a tracing bug, not a capacity problem.** One span name made about 97% of all spans: `evalsha`, the room's commit script. A room commits each step (every stroke) from its actor goroutine, outside any trace, so the Redis instrumentation made each commit a trace of its own, about 650 traces a second at 80 rooms. The design already said "trace rounds, not strokes". The fix is a sampler that drops Redis calls with no parent span, narrow on purpose: heartbeats keep their traces, so the lobby's log lines still point at traces that exist.
- **A crash can poison its own restart.** Tempo also died within a minute of an idle restart. At startup it resumed a stuck compaction of two 360,000-trace blocks, needed over 3 GiB, got killed, and repeated that on every start. Cutting the volume stops new blocks like these, but the stuck ones had to be deleted once. "Restart it" doesn't fix state that a crash left behind.
- **A health check that skips what it can't reach can't see a crash.** The image's healthcheck treats "connection refused" as "this optional part isn't running", so a dead Tempo passed. The compose healthcheck now requires Tempo's and the collector's `/ready`. The collector also got a `memory_limiter`: while Tempo was down, its export queue grew without bound. With the limiter it refuses data, and the SDKs back off.
- **The span attributes were a leak too.** By default the Redis instrumentation puts the full command in `db.statement`. For the commit script that's the room's events and snapshot, and for the ticket redeem it's the join ticket. It's off now. Defaults in instrumentation libraries are written for debugging, not for production data rules.

### Task 5.4: Frontend performance

- **Lab numbers and field numbers answer different questions.** Lighthouse loads two pages on an emulated mid-range phone, three times, and takes the median: it's repeatable, so it catches a regression in the bundle or the server's headers. Real-user monitoring (the browser's own LCP, INP and CLS, plus the room's WebSocket round trip) shows what players actually get, on their devices and networks. INP only exists in the field, since it needs a real person's clicks. So the project has both: `make lighthouse` and `web.vitals.*` in Grafana.
- **Measuring must not slow down what it measures.** The OpenTelemetry SDK and web-vitals are 28 KB gzipped, a third of the app. They load with a dynamic import after the page's load event, so they never compete with the first paint. Round trips measured before the SDK arrives wait in a capped queue of 50. Each page load sends deltas, flushed with `sendBeacon` when the page is hidden. The collector's `delta_to_cumulative` turns every browser's deltas into one series per page, which is what Prometheus expects.
- **A public metrics endpoint is an attack surface for cardinality.** Anyone can post OTLP to `/otlp/v1/metrics`. The browser gets its own receiver and pipeline, and a first version filtered only the metric names and the `page` attribute. A security review then found more ways to mint series: the resource attributes, the scope, the unit, the metric type, the bucket bounds and exemplars. Each one now gets pinned or checked, and I tested each with a crafted payload. The gateway adds POST only, a 64 KB limit and 2 requests a second per address. One OTTL quirk: a slice compared with a list literal is never equal, so the bounds check compares formatted strings.
- **The first Lighthouse run found a missing basic.** Nothing on the path compressed anything: not the ALB, the gateway or the web app's nginx. So the 279 KB bundle went out raw. Gzip at level 6 in the web app's nginx brings it to 85 KB; the default level 1 gives 102 KB. Hashed assets are cached for a year, so the extra CPU is spent once per file per browser.
- **Rejected: Lighthouse as a per-PR CI gate.** A shared GitHub runner's CPU varies from run to run, so a gate either flaps or needs thresholds too loose to catch anything. And the local image has no API behind it. The command runs against the production image for quick checks and against the AWS stack for the numbers recorded in `docs/performance.md`. How it fails: it's manual, so a regression can land unnoticed until someone runs it, and the field vitals on the overview dashboard are the backstop. A browser that blocks `sendBeacon`, or never hides the page, sends nothing.

### Task 5.5a: Kafka users and ACLs

- **Authentication alone wouldn't have helped.** Kafka was the coin mint: whoever could write `game.matches.v1` could pay anyone. "Only authenticated services" still lets the AI service or a compromised lobby write it. What closes it is authorization per topic and per consumer group: each topic's producer writes it, its consumers read it in their own group, and nobody else can do anything (deny by default). Joining someone else's group is as bad as forging an event: you can commit their offsets past records they never saw.
- **The bootstrap problem.** The broker needs an admin credential before anyone can create users, but SCRAM credentials live in the metadata log the broker serves. Kafka's answer (KIP-900) is to write the first credential when the storage is formatted, which the official image's start script can't do. So the broker gets a small entrypoint of its own that writes an explicit config. The controller listener uses SASL/PLAIN with a static user on localhost, so nothing has to be an `ANONYMOUS` super user.
- **The negative test is the real test.** `make kafka-acl-check` tries what each service must not do and expects the right refusal: lobby writing matches, assets joining the marketplace's group, the marketplace creating a topic, the game server changing retention. It caught two bugs in the check itself, never in the broker. An idempotent producer is refused at InitProducerId before the topic is even checked, so the check turns idempotence off to see the topic's own denial.
- **Testing the AWS shape without AWS.** TLS only exists in AWS, where a session costs money and a mistake costs a teardown. A local broker with an openssl CA found the one real bug: the broker's own inter-broker client needs the CA, and it checks that at startup. Each client library was also proven to refuse an unrelated CA. Go happily trusted the server's own leaf certificate placed in the root pool, which made my first "wrong CA" test meaningless.
- **Rejected: mTLS now, and per-event signatures.** mTLS would also encrypt local traffic, but it needs a CA and certificates in every environment. It fits better together with ADR 0006's gRPC upgrade, and the ACLs don't change when the mechanism does. Signing each event adds nothing once only one principal can write a topic: a compromised producer holds its own key anyway. How it fails: an authenticated game server can still send a wrong result, so the marketplace keeps its contract checks; and the admin password is all-powerful.

### Task 5.5b: data ownership enforced

- **A convention is one bug away from a breach.** "Database per service" was true in Postgres from the start: one role per database, `CONNECT` revoked. But Redis had no users at all, and SeaweedFS had one identity that could do anything. Any service, or anything that compromised one, could read join tickets, rewrite a room's events, or forge a stroke log that becomes a drawing. Now Redis has one ACL user per key prefix, and SeaweedFS one identity per bucket, scoped like the IAM task roles in AWS.
- **The details are where ACLs bite.** A test Celery app against a locked-down Redis showed why. kombu prefixes every key and channel when told to (`global_keyprefix`), but Redis checks a `PSUBSCRIBE` pattern literally against the ACL, not as a glob, so Celery's two patterns had to be listed exactly. A second bug only showed on the full stack: Celery prefers the `CELERY_BROKER_URL` environment variable over its configuration, and that variable silently dropped the user I had added to the URL.
- **Positive controls make negative tests honest.** `make data-acl-check` tries 11 things services must not do. Each service also does its own thing first, so a refusal can't just be a failed login. After the full set of drills, Redis's ACL log holds only the check's own attempts: no real traffic was refused.
- **Hash tags are about the future cluster.** The leaderboard script touched two keys in different slots, which Redis Cluster refuses. Both keys now carry the week as a hash tag, `lobby:leaderboard:{2026-W43}`. The match's week comes from its end time, so a redelivery finds the same marker. I fixed only what the review named and wrote down the rest: the lobby's room scripts still span untagged keys.
- **Rejected: one Redis per service.** It would isolate completely, but it means five Redis processes locally and on the data host, for data that's tiny. ACL users give the same ownership with one process. How it fails: the `admin` password opens everything, and a service can still corrupt its own prefix.

### Task 5.5c: a graceful stop drains

- **A deploy shouldn't look like a crash.** Before, SIGTERM closed every room. The lobby noticed only when the heartbeats stopped (6 s) and then moved the rooms by failover, so every player of a stopped server was cut off for all of it: 16 to 17.5 s in AWS. Now SIGTERM drains. The server takes no new rooms and tells the lobby at once, and it keeps running its rooms until each one has moved. In AWS, 41 rooms left within 6.8 s, and the drill's players were disconnected for 0.5 to 2.0 s.
- **No new protocol.** A handoff could have meant snapshotting, sending state to the new server, and a two-phase switch. None of that was needed. The room's state is already in Redis after every step, and the takeover with fencing (ADR 0007) already guarantees one writer. The new owner takes the lease by force, and the draining copy's next commit or renewal fails and stops it with `room_moved`. The only changes were "draining" meaning "move all its rooms" in the lobby, an immediate heartbeat, and a wait before the old shutdown sequence.
- **Measure what the user feels.** The old drill measured from the stop to the resume. For a drain that clock is wrong: the room keeps playing until it moves, so the number that matters is the gap between the socket closing and the new server's first message. Locally, on a laptop where both servers share the CPU, the drain looked worse than a kill (rooms left over 14 s). Capped like AWS, players were disconnected for 5 to 7 s instead of 13. In AWS, with separate CPUs, it was 2 s.
- **Rejected: draining by the RPC only.** A deploy script calling `DrainServer` before stopping a task is cleaner on paper. But ECS, Compose and a scale-in all just send SIGTERM, so most stops would have stayed failovers. The RPC remains for an operator. How it fails: with nowhere to move the rooms (one server, or the other one full), the drain waits 45 s and then degrades to the old failover. In AWS, the surviving server's 100-room cap refused new rooms until the replacement task came up.

### Task 5.5d: one Go module, a flake pass, a README read cold

- **The refactor that removes a real risk.** Agents copy code: the token verifier, the logger, the Redis test helper and the Kafka auth helper each existed in two or three Go services. That had already bitten once, when the JWKS fix had to be applied to every copy. Now they live once in `libs/go`, reached through a `replace` directive like the generated contracts, with the Go images built from the repository root. The one real difference, the notifier requiring `iat`, became an explicit, tested option instead of a silent fork. Rejected: publishing a versioned module, which is overhead for one repository.
- **A flake pass is a test of the tests.** Running every suite repeatedly under extra load found one failure in 33 suite runs, and it wasn't in the code under test. Two packages starting containers at the same moment raced on Testcontainers' shared reaper. In CI that's a random red build that teaches people to press rerun. The fix is a three-try start in one shared helper, used by every harness.
- **When a flake can't be reproduced, make the next one explain itself.** assets' MongoDB container once never answered for 60 s and never failed again in five runs. Rather than guess, the fixture now starts a fresh container once and prints the dead one's last log lines. It also checked the obvious suspect: the local kernel is past MongoDB's known bad range, while CI stays pinned to a runner outside it.
- **"Understood in five minutes" can be tested.** A reader given only the README answered five newcomer questions correctly, then listed what tripped it up: a claim that three parts were built when the third is next, terms used before they're explained (lease, fencing token, outbox, claim check), and a comparison of AWS numbers with local ones. Each was fixed. How it fails: a README drifts as fast as the code. The README links to performance.md and the roadmap for numbers rather than copying them all.

### Follow-up to 5.5: seeing who knocks on Kafka

- **Count at the server, not in the clients.** The plan was a counter in every client, in Go, Python and Java. But the client that matters most, an attacker's, isn't ours and reports nothing. The broker sees every failed login and every refused request, so the OpenTelemetry Java agent in the broker exports them through JMX rules and ships its log, where each denial names the principal. That's one place and no per-language code.
- **A metric with a baseline can't be a threshold.** The authorizer's denied-requests rate read 33 a minute on an idle, healthy stack: it also counts topics it quietly leaves out of metadata answers. Alerting on it would always fire. The alert uses the logged denials, which are the real refusals, plus failed logins, and only when they last 5 minutes, so CI's own ACL check (a 10-second burst) never trips it.
- **"Admin should never be used" needed admin to be distinguishable.** Idle, the broker itself made 47 requests a minute as admin: its own controller heartbeats. So the broker, the init job and humans got separate super users. The first idea for spotting admin, logging allowed requests at DEBUG and filtering for admin, failed in testing: the agent captures log events before the filter, so every authorized request would have flooded Loki.
- **The better fix also hardened it.** admin lost its SCRAM credential and now exists only on a localhost listener inside the broker container. It can't be used over the network at all, and that is a new case in the ACL check. Every admin login shows up on that listener's successful-login counter. A human runs `kafka-admin`, and the alert fires 55 s later.
- **Migrations count too.** The shared stack's broker predated the new users, which caused two problems. Its healthcheck would log in as a user that didn't exist yet, and kafka-init, which waits for a healthy broker, would never run: a deadlock. So the healthcheck falls back to the old credential, and kafka-init adds the users once, then deletes admin's network credential. How it fails: anyone with a shell on the broker container is admin, so the alert is a tripwire, not a lock.

### Follow-up to 5.5: ready for Redis Cluster

- **A one-node cluster is enough to test cluster rules.** Redis Cluster refuses a transaction or Lua script whose keys hash to different slots (CROSSSLOT), and a single node that owns all 16384 slots enforces that just like a real cluster. So the test starts one in a container and runs every lobby call that writes several keys at once. It also runs one deliberately untagged transaction as a control, which must fail, so the test can't pass by accident. With master's keys the test fails in exactly the places review had pointed at.
- **One slot per group, on purpose.** The lobby's room index (room records, the public list, each server's room set, the host set) changes together in one transaction, so it shares the tag `{rooms}`, and the registry shares `{registry}`. That puts each group on one node of a future cluster. That would be a hot spot for a busy table, but this is a handful of small records per open room. The game server's data, the real volume, was tagged per room from day one.

### Stage 5 review

- **A managed policy can grant more than you wrote.** The data host's own policy allowed only its secrets, but AWS's Session Manager policy, attached for shell access, allows `ssm:GetParameter` on every parameter. The one container that could use the role also takes public browser telemetry. An explicit Deny with `NotResource` fixed it: in IAM, a Deny always beats an Allow, so whatever a managed policy adds later can't widen it.
- **Credentials don't help if the side door is open.** SeaweedFS had one S3 identity per bucket, but its filer and master ports take no credentials at all, and every container shared its network. A network of its own (as Kafka has) makes the identities mean something, and the check proves it from both sides: assets reaches the filer, a service outside can't even resolve the name.
- **A drain only works if something can take the rooms.** The drain was correct for one server, but a deploy replaced both game servers in the same apply, so each was draining into the other. A redeploy now holds game-server-2 at its old image until game-server-1 is stable. The same trap catches any rolling deploy: the replacement capacity has to exist before the old capacity leaves.
- **A check that can't fail proves nothing.** The "no credential is refused" Kafka case passed on any failure, including a broker that was down. It now first proves the broker answers a valid credential, the same control pattern the Redis and S3 checks already used. A teardown script got the same treatment: it now checks for anything still billing instead of trusting terraform's exit code.
- **Doc drift is a bug class of its own.** Four PRs into one task, older docs still described the first design (admin as the bootstrap user), and two runbooks used a Kafka command the broker has refused since the ACLs landed. A runbook is code that runs during an incident, when nobody has time to debug it.

## Stage 6: Scale and depth

### 6.10 AWS data across sessions

- **The problem: a stateless stack that people now put data into.** The AWS stack is created and destroyed per session to keep the cost at cents an hour (ADR 0003). Once strangers could play, every teardown deleted their drawings, coins and trades. A drawing can't be kept alone: its owner and the coins that paid for it live in other services' databases, so the backup covers all of them, taken while nothing writes.
- **Back up logically, and restore every session.** The other options kept a disk or a snapshot, which would carry the old session's database passwords into a stack that makes new ones. A `pg_dump` restored with `--no-owner --role=<service>` belongs to whoever restores it. Because every `aws-up` restores, the backup is tested every session instead of on the day it's needed. The recovery point is the last teardown, and the restore time is measured.
- **The backup gates the destroy, and the manifest is the commit marker.** Nothing is destroyed until every dump has been read back, uploaded with a SHA-256 that S3 itself verifies, and its checksum and size re-checked from the laptop. The manifest is written last, and a backup without one is never restored. The restore must also match every table's row count in the manifest. The failure that prompted this was a teardown that lost its network halfway.
- **Least privilege again found the risky container.** The dumps run on the data host, whose role otel-lgtm can also use, and otel-lgtm takes public browser telemetry. So that role may only put dump files: it can't read a backup, and it can't write a manifest. Restores download through presigned URLs that the human signs for 15 minutes. A security review flagged the first version, which would have let a broken-into host forge a backup.
- **How it fails.** An event already in Kafka but not yet consumed at teardown is lost; the writers stop first and the script waits for the lag to reach 0 to make that window small. A backup with a migration the code lacks is refused; the check compares migration ids, not git ancestry, which a rebase would break. Retention is by count (the newest 10), because an age rule would delete the only backup after a long break.

### 6.1a Live rooms through relays

- **The problem: one room, thousands of sockets.** A room is one actor that commits each step to Redis, then sends it (task 5.3: about 20 four-player rooms per 0.25 vCPU). Fanning one room out to thousands of viewers on its owner would slow the players' own game. Relays separate the read path from the write path. The owner keeps processing every input alone, and relays only read the room's Redis stream with `XREAD BLOCK` and fan it out. The owner doesn't know they exist, so a takeover changes nothing for viewers.
- **Encode once, queue to everyone, never wait for anyone.** A relay's stream goroutine encodes each event once and puts it in every viewer's bounded send queue. A viewer whose queue fills is closed and resumes; it can't hold back the others. The test proves it with about 20 MB of strokes. A viewer that stopped reading couldn't even receive its close frame, which is why the test counts `relay.viewers.closed{reason=slow}` instead of checking the close code.
- **The secret is safe by construction, not by filtering.** A viewer's welcome is the room rebuilt from its snapshot and events (`room.ViewAt`), then viewed as a guesser. Shared events never contain the word before `round_ended`, so a relay can forward them unchanged. The test checks both a welcome built mid-round and every event before the round ends.
- **Least privilege again, this time between roles.** A viewer's ticket is the lobby's Ed25519 ticket with a different audience (`doodle-watch`). Game servers have always required `doodle-game`, so a viewer's ticket can't take a seat even on a server older than the feature, and a relay refuses a player's ticket. That beat adding a role claim, which every old verifier would ignore.
- **Two bugs the drill found that unit tests didn't.** First, heartbeats every 2 s made a burst of viewers all land on the relay that was least loaded at the last report: the lobby now adds the tickets it issued since each report. Second, a viewer resuming on a relay that had just started got a full welcome: a stream now preloads the room's last 200 events. Both are distributed-systems classics: stale load reports, and state that only one node held.

### 6.1b The watch page

- **A viewer is a player who can't act, so the client barely changed.** The room connection already took its "get a ticket" function as a dependency (for tests). Watching is the same connection with the lobby's watch call: the same backoff, liveness checks and `last_seq` resume. The same pure reducer renders the room from the same events, because a relay forwards exactly what players get. The page only hides what a viewer can't do.
- **The browser, not the unit tests, found the idle timeout.** With a long round, the drill's bots were closed after 60 s: the game server closes sockets that send nothing for a minute, and the bots never pinged, unlike the web app. Unit tests run for seconds, so only a realistic run showed it.
- **Not everything new needs a new label.** The watch page reports Web Vitals as the room page, because a new `page` value would have meant changing the browser collector's allow-list. That allow-list stops arbitrary label values from public, unauthenticated telemetry.

### 6.1c Measuring thousands of viewers

- **The first bottleneck wasn't in the system.** At about 2,000 viewers the relays' p99 shot up, but a CPU profile showed a relay using under one core, and the players' own fan-out, which never touches a relay, got slow too. A shared slowdown in a part that wasn't loaded pointed at the test bench: every message also crossed Docker Desktop's proxy between macOS and its VM. Running k6 inside the stack's network removed it. Lesson: before tuning, check that the thing you measure is the thing that's slow.
- **Then the load generator.** 3,000 viewers at 40 events a second are 120,000 messages a second for k6's JavaScript event loops. It fell behind, buffered the backlog, and was OOM-killed. A slow reader also inflates the server's numbers, because the relays' writes back up behind full receive buffers. Even exporting k6's per-message samples doubled its CPU and made the relays look 13 times worse. The decision: record what one laptop shows honestly (2,000 viewers under the target, 2,500 depending on contention), and measure 5,000 where generator and system don't share a CPU (AWS, task 6.9).
- **Measure on the server and say exactly what it covers.** The target is the relays' own histogram, from the owner's commit until the write to the viewer's socket returns. The client number also counts the generator's lag. Both are recorded, and the M6 claim uses the one that measures the system.
- **What would scale a relay further.** Each event costs one goroutine wake-up and one syscall per viewer. Coalescing a few events per viewer per write (tens of milliseconds) trades a little latency for far fewer syscalls; that's task 6.4's batching experiment. Adding relays is the other lever: the lobby already spreads viewers across them.


### 6.5a Flink and the top-guesses job

- **Event time, not arrival time.** A guess counts in the window of when the relay received it (`guessed_at`), not when Flink read it. Watermarks say "no guesses older than this will come" (2 s of out-of-orderness), and a window is reported only once the watermark passes its end, so the output is final and append-only. The cost is that a quiet room's last window waits for newer guesses. An idle partition stops holding the watermark back after 10 s, and a guess that arrives after its window closed is dropped and counted.
- **SQL where it fits.** "The five most common guesses per room over the last 30 seconds, every 2 seconds" is a hopping window TVF, a window Top-N with `ROW_NUMBER`, and one more aggregation that folds a window into one row. The planner turns that into windowed state that it cleans up by itself. Wash trading needs per-drawing state and timers, so it gets the DataStream API in 6.5b. That shows both APIs, each where it fits.
- **Why at-least-once is enough here.** A Kafka transaction would hold each list back until the next checkpoint (30 s), which defeats a live list. Instead the output is made safe to repeat: a `TopGuesses` replaces the room's previous one, and its `event_id` is a UUID derived from room, round and window end, so a replayed window is recognizably the same event.
- **Version constraints are part of the design.** Flink 2.3 is out, but no Kafka connector supports it, so the service runs 2.2.1. The official image runs Java 21, while the shared generated code targets Java 25 for the marketplace. A Gradle toolchain plus compiling only the event classes the job uses kept both services on their own JDK without forking the contracts.
- **Running out of memory is an architecture question too.** Adding two JVMs pushed the full stack past an 8 GB Docker VM. Measuring first showed where memory went: otel-lgtm's 2 GB was mostly page cache, while the JVMs had grown to their default heaps. Capping the JVMs and making relays and Flink opt-in compose profiles kept every check runnable on a laptop. CI turns both profiles on.

### 6.5b Wash trading and keeping state across restarts

- **A domain fact made the algorithm simple.** A drawing has one owner, and only the owner can sell it, so a drawing's sales form one chain where each buyer is the next seller. A loop is then just "this buyer sold this drawing before, within 7 days", and the sales in between are the loop. That covers R1 (two hops) and R3 (three or more) with one check, keyed by `drawing_id`, without a graph search.
- **Event time decides, the watermark only cleans up.** Whether a sale is inside the 7 days is computed from the sales' own times. Timers drop old sales when the watermark passes them, and on quiet topics that can be late, but late cleanup costs memory, never a wrong flag. Sales are rare, so the watermark is a poor clock for correctness here.
- **Checkpoints don't help if nobody restores them.** Without high availability, a new Flink JobManager starts every job empty, so 7 days of history would be lost on a container restart. The job's `main` now finds the newest completed checkpoint through Flink's own file system and starts from it in CLAIM mode. ZooKeeper or Kubernetes HA would do the same with another system to run. The drill restarts Flink between two sales of one loop and still gets the flag.
- **The first restore failed, and that taught something.** Flink SQL generates its operators' ids, and adding the sales pipeline changed them, so Flink refused to map the old state. The fix splits state by value: the SQL windows (30 s of top guesses) may be dropped, while the sources' offsets and wash trading have fixed uids and must restore. In production, a pinned uid is part of the state's contract.
- **Testing an alert end to end found a monitoring bug.** After a restart, Flink's counters are new series, and one that counts before its first export starts at 1, so `increase()` sees nothing. The wash-trading alert therefore counts series that are new in its window by their whole value. A unit test of the job couldn't have found this; only real sales, a restart and a look at the alert did.

### 6.2 Viewer guesses and the first correct viewer

- **Who decides "first" in a distributed system: the one writer.** Viewers sit on several relays, but a room already has exactly one writer, its owner, fenced by a token. So relays only check guesses and forward the correct ones through a Redis stream. The owner's actor takes the first one for the round and writes `viewer_correct` through the same fenced commit as everything else. A relay-side `SET NX` would have been simpler, but it would put a decision outside the event log, so replays and takeovers wouldn't see it.
- **Idempotency by meaning, not by cursor.** A new owner reads the viewer-guess stream from the start instead of tracking a cursor. That is safe because the restored game already knows the round's winner, and a stale entry is ignored. The security review showed what "the round" must mean: round numbers restart every match, so a guess has to name its match too, or an old match's guess could win a new round.
- **Keeping the secret secret on every path.** Wrong guesses feed a top-guesses list every viewer sees, so the relay never publishes a correct guess or one containing the word. Two less obvious leaks came out of review: the drawer watching their own room as a viewer, and a viewer who knows the word reconnecting to guess again. Both are now refused, by user and by seat.
- **Least privilege for the public edge.** Relays face thousands of anonymous-ish sockets, so they got their own Kafka and Redis users. Kafka allows writing viewer guesses and reading top guesses, and nothing else. Redis allows reading rooms and writing viewer tickets and viewer guesses, and nothing else. A compromised relay can't mint coins or forge room events, and the ACL checks prove it in CI.
- **Never let a side effect slow the hot path.** A relay's stream goroutine fans each event out to thousands of viewers, so guess handling must not block it. Kafka produces use `TryProduce` and are dropped when the buffer is full. Correct guesses go through a bounded queue and one worker, and stop once the winner is known: only the first matters.

### 6.6 Data scale: query tuning, partitions and a read replica

- **Measure on realistic volume, and look at the plan the app really gets.** `make seed` writes about 5 million rows through the same triggers and constraints the services meet, so reconciliation stays at 0. The surprise in `EXPLAIN` was a query that looked fine: "a seller's active listings" took 0.06 ms by hand, but its optional filters were written as `CAST(? AS ...) IS NULL OR col = ?`. After five executions the JDBC driver prepares it on the server, and Postgres may switch to a generic plan that can't use an index for any parameters: 48 ms, reading all 50,000 active listings. Building the SQL from only the filters given made it 0.01 ms. A covering index sped up the ownership check from 1.4 s to 1.0 s, and an index that `EXPLAIN` never used was left out, because it would only slow writes.
- **Partitioning is about bounding work, not speed by itself.** Over the partitioned ledger the old full-scan reconciliation got slower (66 to 153 ms: an append over every monthly partition). The gain came from what partitions allow: a closed month's per-account totals are stored once, and each run scans only the open months. To keep stored totals honest, each run re-verifies the oldest-checked month, so tampering a superuser could do still shows up within hours. The key detail is that a posting's entries share one `created_at`, so a transaction never spans two partitions, and the balance trigger prunes to one.
- **Read-your-writes by WAL position, not by a timer.** A successful write returns the primary's WAL position in a cookie. A read goes to the replica only if it has replayed past that position, otherwise to the primary. The alternatives were "primary for N seconds after a write" (a guess at lag, wrong in both directions) and "personal pages always on the primary" (most reads would stay there). The cookie covers both the marketplace and assets, because they share one Postgres server and so one WAL.
- **A replica can lie by being quiet.** A replica that lost its connection to the primary has replayed everything it received, so it looks caught up to itself, and the service roles can't read `pg_stat_wal_receiver` to tell. A security review caught that this could keep showing a drawing a moderator had rejected. The fix bounds staleness without any privileges: each process samples the primary's WAL position at most once a second and requires the replica past what the primary had 5 s ago. Reads then fall back with reason `stale`, which the alert counts.
- **How it fails.** A replica that is down costs a read one second at most (connect timeout), then the primary. A replica that falls behind sends reads to the primary, which then carries the whole read load. A replication slot pins WAL while the replica is gone, capped at 1 GB, after which the replica must be recloned (runbook). A posting outside the pre-created partitions lands in the default partition and blocks creating that month's partition, so it has its own alert and a rehearsed fix.

### 6.3 Tips and the hot wallet

- **The problem is one row.** Every ledger posting locks the balance rows it touches, so a thousand viewers tipping one drawer queue on the drawer's row, one commit at a time. Measured: 1,000 tips to one drawer on 32 connections reached 361 a second with a p99 of 521 ms. The same tips into 16 escrow accounts reached 987 a second with a p99 of 147 ms, and one 38 ms settlement then paid the drawer.
- **Batch by a domain boundary, not a timer.** A round already has an end, and the game server announces it with `RoundFinished`. So tips wait in escrow and are paid once per round, in one posting that locks the drawer once. Using the game server's event also settles who gets paid: the authoritative server names the drawers, so a client can't tip itself to someone who isn't drawing. Per-drawer sub-accounts would also spread the locks, but they'd still need the client to name the recipient, plus a new contract to check it.
- **Every money path needs its exits.** Escrow brings states that direct posting doesn't have, and each one needed a rule:
  - a round that never finishes (a match that ends during word choice publishes no `RoundFinished`): refunded after 10 minutes;
  - a tip that commits just after its round was settled: paid by the sweeper to the same drawers;
  - a drawer tipping their own round, or a tip naming the wrong room: refunded in the settlement itself;
  - each settlement's idempotency key: counted on the round's row, which only settlers lock, so tippers never wait for them.
- **Escrow is a system account, so the database won't stop it going negative.** The reconciliation job got a fourth invariant: each shard holds exactly the sum of its pending tips. A test tampers with a tip's status and expects the alert.
- **Load tests find what you didn't change.** The k6 run's tail (p95 344 ms) wasn't locks, whose p99 was 23 ms. It looked like the JVM's Serial GC, picked by its 1 GB container limit; the follow-up below found one specific full collection and a connection-pool queue. A separate gotcha: the gateway's per-address rate limit means one load generator can't measure a crowd through it, so k6 calls the marketplace on the stack's network and says so.

### 6.3 follow-up: the marketplace JVM's pauses

- **Read the GC log before tuning the GC.** The metrics said "Serial, full collections, about 1.5 s", which pointed at heap size. The JVM's own log gave the cause: `Pause Full (CodeCache GC Threshold)`. After JDK 20 removed the code-cache sweeper, the JVM collects to unload old compiled code once the JIT has added 15% of the code cache. Serial can only do that in a full collection with class unloading, and with 98 MB of Spring and agent classes that took 1.4 s, once per JVM. One flag (`SweeperThreshold=50`) moved the threshold past what warm-up compiles, and the longest pause dropped from 1.45 s to 95 ms.
- **The right collector depends on the CPU, not the heap.** G1 would have unloaded that code concurrently. But the ECS task has 0.5 vCPU, which the JVM sees as one processor, so G1's concurrent threads would compete with the requests for that core. Serial with a fixed heap fits: young collections every few seconds instead of every 0.6 s, and no full collection to grow the heap.
- **Container memory isn't all heap.** Metaspace, code cache, threads and the OpenTelemetry agent take about 350 MB of the marketplace's 1 GB. The old 75% heap ceiling (768 MB) would have hit the container limit the first time the heap grew that far. So the heap is fixed at half.
- **Fixing one cause showed the other.** With GC pauses gone the tail stayed, and it followed Postgres' time per connection checkout, not GC time. Each tip takes three checkouts (claim, posting, completion). That's 900 a second on a 10-connection pool, so any slowdown from a busy laptop fills the queue. More connections didn't help: a Postgres short of CPU doesn't go faster with more clients.
- **Read metrics per process.** Counted with one `increase()` over the service, restarts hid full collections, because several JVMs share an instance id. Read per JVM (by `host_name`), every JVM had exactly one.

### Remote dev box (GCP)

- **A laptop isn't a deployment target, and neither is a dev box.** The full stack needs about 9 GB in Docker's VM, more with Testcontainers and k6, so a 16 GB Mac ran out of memory. A 32 GB Compute Engine VM runs the stack and the end-to-end checks; the Mac keeps single-service tests, CI stays the gate, and AWS stays the only deployment. It needed no ADR, because nothing in the system changed.
- **No public ports, even on a dev box.** The VM sits on its own VPC whose only ingress rule is SSH from Identity-Aware Proxy's range; Grafana, the gateway and Postgres are reached through SSH port forwarding. It has no service account, so a compromised container can't call a GCP API, and GitHub access is a read-only deploy key, so it can pull but never push.
- **Guardrails first, as with AWS.** The budget tracks spend with credits excluded (by default a budget nets out credits and reads $0 for the whole trial), and an instance schedule stops the VM every night. The schedule only works once the Compute Engine service agent may stop instances, which fails silently otherwise.
- **The same stack on a new host found two assumptions.** MongoDB 8.0 refuses kernels 6.19 to 7.0.13, so the VM runs Debian 13 (kernel 6.12) and not Ubuntu 24.04, as CI's stack job runs 22.04. And Linux exposed what Docker Desktop hid: Go's `-race` needs gcc, and the web container's `node_modules` volume leaves an empty root-owned folder on the host, which `make test` had taken for installed dependencies.
- **Swapping one service out of a running system is a networking exercise.** To run the marketplace on the Mac against the VM's stack, the gateway must still find `marketplace:8080`: a two-line nginx stream proxy takes over the network alias and sends connections through a reverse SSH tunnel bound to Docker's bridge address. Kafka decided the rest: a broker hands clients its advertised address (`localhost:9094`), so that port on the Mac has to be the tunnel, whatever port the client first dialled.

### CI: a two-tier stack job and merge-first

- **Measure the pipeline before tuning it.** The 15–18 minute stack job broke down as about 4 minutes of image builds with zero cached layers, 71 s of `kafka-init` that most services wait for, 1.5–2 minutes deleting preinstalled toolchains, about 6 minutes of checks run one after another, and 52 s of `make down`. Two of those were pure waste: the disk cleanup was written for a runner that was 94% full, and the current one starts at 41%; tearing down a runner that is about to be thrown away gains nothing.
- **Tier checks by what they protect.** The core (health, telemetry, the drawing pipeline, Kafka and data ACLs, alert rules) catches a broken stack and runs on every PR. The feature drills and load-test smokes each test one feature, take about five more minutes, and run on `master`, on demand, or on a PR labelled `full-stack`. A label is a cheap, visible switch a reviewer can flip.
- **A concurrency group can cancel the run you wanted.** Adding the label trigger meant every label event starts a run in the PR's group, and `cancel-in-progress` would let an unrelated label cancel a real run before the job's `if` skipped it. Unrelated labels now get a group of their own; `full-stack` shares the group on purpose, so it replaces a core run in progress.
- **Merge-first is a deployment question, not a CI question.** It's safe here because nothing deploys from `master` (AWS changes only through `make aws-*`), the trunk takes one task at a time so a red run points at one merge, and a revert is one button. The rule still keeps waiting for the risky areas: infra, ACLs, migrations, money paths, fencing and contracts.

### 6.8a Limited drops: no overselling

- **Keep the burst away from the truth, but never trust the gate.** A drop is many buyers racing for few editions. Redis handles the race:
  - a read-only Lua look answers "not admitted" or "sold out" before a request claims anything in Postgres;
  - a reservation script hands out edition numbers atomically.

  Postgres still decides every sale, behind `PRIMARY KEY(drop_id, edition_no)`, `UNIQUE(drop_id, buyer_id)` and `CHECK(edition_no BETWEEN 1 AND editions)`. The test proves it by making Redis lie: every edition number is handed out three times to 300 buyers, yet exactly 20 editions sell, 20 buyers are charged, and 40 extras are refused with their coins rolled back.
- **Fairness is a design choice, not a side effect.** First come, first served rewards bots and refreshing. The waiting room gives everyone who joins before the open a random place, then admits places at a rate that is a pure function of time, so no job runs and no clock has to tick.
- **A classic trap showed up in the baseline.** The Postgres-only comparison first locked the drop's row and counted its sales in the same statement. Under READ COMMITTED, a statement that waited for a lock still counts with its old snapshot, so two buyers saw the same count. Taking the lock in one statement and counting in the next fixed it. That's why the real design never counts under a lock at all.
- **Two stores, one rule: disagreement may cost an unsold edition, never an extra one.** Every failure has its path:
  - a rollback gives the reservation back;
  - an edition Postgres already sold is forgotten, not returned;
  - a reservation leaked by a crash is released by the sweeper after a minute;
  - a Redis that lost its data is restocked from Postgres;
  - a Redis that's down makes drops answer 503 rather than guess.

  A security review found one more case: a buyer Redis forgot took a new edition that was then marked theirs and lost. The fix gives it back and relearns the edition they own.
- **The payout reuses the tips pattern** (ADR 0021): buyers' coins go to 16 escrow accounts, so no author's balance row is hot, and one posting per batch pays the authors once the drop sold out. A closed drop that didn't sell out waits a minute first, because a purchase that passed its window check just before the close may still be committing.

### 6.8b The flash sale, measured

- **No overselling holds at scale, three times over.** On the dev box, 1,000 seeded buyers raced for 100 editions. Every run sold exactly 100 to 100 distinct buyers, and the check afterwards counts in Postgres, not in k6: 100 edition rows, 100 purchases charged, the authors paid 1,000 coins, and the ledger summing to 0.
- **The first run found a waiting-room bug in how answers were ordered.** The read-only check said "not admitted" before "sold out". So once the editions were gone, everyone further back in the queue kept retrying for up to 20 seconds: 9,726 requests for 1,000 buyers. Answering "sold out" first cut it to about 3,100. It's a small reorder in a Lua script, with a visible effect on load.
- **Read the tail before you tune.** p95 was 1.2 s on a warm JVM and 2.1 s right after a rebuild. All 1,000 buyers fire within 200 ms of the open, about 5,000 requests a second for an instant, at one 1 GB marketplace. Redis's scripts take well under a millisecond. So the tail is the burst queueing at one instance, not the inventory design. The fix is more instances, not a different lock. The k6 threshold now asserts what matters (exactly N sold, no errors) and bounds latency loosely.
- **Cold starts are part of the measurement.** The first drop on a freshly seeded box got a 503: the marketplace's very first Redis call had to open the connection and log in within its 500 ms timeout. The connection now opens at startup, and the rebuilt-then-measured run shows how much a cold JIT costs under a burst.

### 6.7 Search

- **Build the document from one place, not from the events.** A drawing's search document mixes assets' data (word, authors, approved or not) with the marketplace's (is it listed, at what price). Its events arrive on three topics with no order between them, so a "patch the document per event" indexer can end in different states depending on the order. Instead, each event updates a small projection of listings in assets' own Postgres, and the indexer rewrites the drawing's whole document from those tables. The projection's rules (a closed listing can never come back; an older listing never replaces a newer one) make every order end in the same state, and a test runs every permutation.
- **External versions make retries and rebuilds safe.** Each change bumps the drawing's `search_version` in the same transaction, and the write to Elasticsearch carries it with `version_type=external`. A retry or a concurrent rebuild holding an older version gets a 409 and does nothing. That's what lets `reindex_search` rebuild into a new index and swap an alias while the indexer keeps running: a catch-up pass rewrites the drawings whose version moved during the build.
- **The search engine ranks, the database answers.** Search returns ids. Assets reads them back from Postgres, keeps only approved drawings, and signs fresh image URLs. So a drawing a moderator just rejected never shows up, even if its delete hasn't reached the index. And when Elasticsearch is down, search answers 503 while the plain gallery and market lists keep working.
- **Rejected alternatives.** Writing to Elasticsearch from the request paths (dual writes) can leave the two stores disagreeing with nothing to repair them. Replaying Kafka can't rebuild either, because topics keep 7 days. Reading the marketplace's database from assets would break database-per-service. So the backfill is an admin endpoint: it re-announces every active listing through the marketplace's outbox, and the same idempotent indexer applies it.
- **Least privilege reaches the search engine too.** Security is on, with two users: the web process can only read `drawings*`, and only the indexer can write. A review caught the first version, where both processes shared one write-capable credential: an exploit in the web process could have rewritten prices in search results. `make data-acl-check` now proves the refusals.

### Fix: the seed and the partitioned ledger

- **An optimization is a set of assumptions; list them.** Task 6.6 partitioned the ledger by month and cached closed months' totals, both resting on one fact: postings take `now()`. The seed backdates a year, so it broke both at once on the dev box: 1.7 million rows in the default partition, and twelve months closed in one second, while the seed had written only its first month. The Mac never showed it, because there the seed ran before the migration that added partitions.
- **A cache has to change atomically with what it caches.** The fix doesn't touch the marketplace. The seed commits its whole year in one transaction, which also rebuilds any closed month it wrote into, under a lock that waits for a close in progress. Reconciliation reads in a snapshot, so it sees all of the seed or none of it, never a balance whose entries sit in a month summed before they existed. LedgerImbalance pages on a single bad run, so "eventually consistent within two minutes" wasn't good enough.
- **Rebuilding the cache can hide tampering.** Re-checking closed months exists to catch a change made behind the triggers' back, and blindly re-summing would erase that evidence. So the runbook rebuilds only after one check: each month's extra entries must be explained by seeded transactions, and entries can only have been added, because the triggers refuse updates and deletes.
- **Keep the cache's shape, not just its sums.** Reconciliation scans only the months after the last closed one, so the closed months must be an unbroken run from the oldest entry. Deleting stale months, my first idea, could leave a gap that hides a whole year if the job closed a month in the same instant. Re-closing every month from the first seeded one up to the last closed one keeps the run whole.
- **Reproduce first, in a sandbox.** A throwaway Postgres on the dev box ran the old and new seeds with the job's own SQL looping beside them. The old one gave 10,001 mismatched accounts at a tenth of the scale; the new one read 0 on every pass at full scale.

### 6.7b The gallery cache

- **Cache what can't go stale, sign what can.** Only approved drawings are cached. A decision is final, so their fields never change, and they look the same to every player. An author's own unapproved drawings never enter the cache. Image URLs expire, so the cache keeps the image keys and the API signs the URLs on every response. The answer is identical with the cache on or off, and a test checks it.
- **Cache-aside has a race, and the generation closes it.** A reader can read the old page from the database, and then a writer commits and deletes the key. If the reader stores its old page after that, everyone sees stale data until the TTL. Instead, page keys carry a generation number that an approval increments after its commit. The reader reads the generation before its query and stores under that one. A reader that raced an approval only fills a generation nobody asks for any more. A test makes the approval commit in the middle of a fill. Pages are filled from the primary, because a lagging replica could put an old page under the new generation.
- **Stampedes: one fill, everyone else waits briefly.** Every approval empties the hot first page at once. A lock with a token (`SET NX PX`, released by a compare-and-delete script) lets one request fill the first three pages with one query, while others poll for up to 200 ms and then read Postgres themselves. The cache never blocks a request for long, and 50 threads on a cold page make one query. I rejected serving the stale page while refreshing it: no request waits, but the old page outlives the approval and needs extra state.
- **Fail open, and measure honestly.** Redis gets 100 ms per call, and after an error the cache steps aside for 5 seconds, so an outage costs one timeout, not one per request. With k6 at 150 requests a second, p95 fell from about 250 ms to about 17 ms and Postgres reads per request from about 1 to 0.16. The ceiling only moved from about 186 to about 290 a second: once Postgres was out of the way, the limit became Python CPU in two sync workers (telemetry, JWT, JSON). That's the next thing to scale, by adding workers.
- **Shared Redis needs discipline.** The cache sits next to Celery's broker in a Redis with no eviction policy, so every key has a TTL: 10 minutes for a drawing, 60 seconds for a page. The whole cache measured 3.5 MB. Postgres stays the only truth: wallets and listings are never cached (D43), because their answers must be exact.

### 6.4 Experiments: batching and wire formats

- **Measure the cost per unit of work, not per run.** The first protobuf run looked like a win on the server (0.58 against 0.96 cores) and a loss on the client. Both were k6: its JavaScript interpreter needed twice the CPU for binary frames, so its timers ran late and it sent 22% fewer batches. After recording k6's CPU and the server's own count of batches received, protobuf turned out to cost the server slightly *more* per batch. The lesson: check that the load generator isn't the bottleneck, and normalize by the work actually done.
- **Smaller frames aren't cheaper if you still encode the old way.** Protobuf cut stroke bytes by about 70%. But the room's event log stays JSON (replays, relays and takeovers read it), so each stroke is marshalled twice, and a batch's real cost is its Redis commit and fan-out, not its encoding. The win is bandwidth, which matters for mobile data or egress, not server CPU. Moving the log to protobuf would be the next step if that ever mattered.
- **Batching is a latency-for-throughput dial with a visible price.** Every batch is one Redis commit and a fan-out. Going from 50 to 33 ms bought 17 ms of ink delay for 38% more CPU and 45% more Redis commands; 16 ms cost almost double. The drawer sees their own stroke at once through a local overlay, so 50 ms only delays what *others* see, and it stays the default.
- **Negotiate, don't break.** The binary format is a WebSocket subprotocol (`doodle.strokes.pb`). A client that doesn't ask gets exactly the old JSON protocol, and binary frames without it still close with 1003. Only stroke batches go binary, encoded once per format per event, so old clients, relays and viewers keep working. Defaults are an ADR decision based on the numbers.
- **Two codecs, one source of truth.** The web app and k6 have hand-written protobuf codecs (about 80 lines; no runtime in the bundle). A Go test writes the server's bytes into a fixture, and the web tests must decode and produce exactly those bytes, so a change to `ws.proto` that isn't carried through fails CI.

### 6.9 Final measurements

- **A fire drill tests the alert, not just the system.** GameServerDown compared `lobby.servers.healthy` with 2, the number of game servers. In task 6.1 relays started registering with the lobby too, so the gauge read 4 and a dead game server left it at 3: the alert could never fire. No test caught it, because each piece was right on its own. Stopping a game server on purpose and timing the alert did. The fix gives the gauge a `role` and points the alert at game servers. In AWS it then fired 160 s after the fault and resolved 66 s after the runbook's fix.
- **SLOs as burn rates.** "5xx above 1% for 5 minutes" says something is wrong now, but not whether it matters this month. The availability SLO (99.5% of API requests without a 5xx over 30 days) has a budget of 0.5%, and the alerts fire on how fast it's being spent. Fast burn is 14.4× over both an hour and 5 minutes, two days to empty. Slow burn is 6× over 6 hours and 30 minutes. The short window makes an alert stop soon after the problem does, and a traffic floor keeps one 500 on an idle stack from paging anyone.
- **Tail sampling decides with the whole trace in hand.** The collector waits 10 s for a trace's spans, then keeps every error, everything over 500 ms, every money path and the synthetic checks, drops health checks, and samples 10% of the rest. A head sampler can't keep "the slow ones", because it decides before anything is slow. The cost is memory for the 10 s window, bounded by `num_traces` and the memory limiter. I also made the lint validate the collector config with the real collector, after an invalid overlay took all telemetry down on the dev box.
- **A public telemetry endpoint must not be a way into backend traces.** The browser's spans go through the same hardened receiver as its metrics. A security review pointed out that a client chooses its own trace ids, parents and status, so it could graft spans onto a backend trace or force its spans to be kept. The collector re-keys trace ids with a hash, clears parents and trace state, fixes the kind and decides the status itself, and the web app sends no `traceparent` to the API. Browser traces stand alone; joining them to the backend would need a server-issued id, not a client-chosen one.
- **Measure the load generator too.** The 5,000-viewer room met its target on the relays (p99 240 ms against 250, the relays at half their CPU). k6 on one VM was the thing that fell behind: 96,000 messages a second, viewer p95 of seconds, and players' own fan-out slowed even though it never touches a relay. Every client from one address also meets the gateway's 20 requests/second per address, which made reconnect storms after a failover look worse than real players would see. The relays' own latency histogram, recorded server-side, is the number that counts, and its p99 is pessimistic when readers are slow.

### Follow-up to 6.9: drain metrics that read zero

- **A counter that is born non-zero is invisible to `increase()`.** An OpenTelemetry counter series appears with its first data point. If 41 rooms move before the first export, Prometheus's first sample is already 41, and `increase()`/`rate()` need a sample before the change, so the dashboard showed a 41-room drain as 0 moves and 0 takeovers. The raw counter was right. The fix is old Prometheus advice: initialize the series you know about at 0 at startup (`Add(ctx, 0)` for each label combination), with a test that the series exist before any event.
- **Check the label's definition before you call it a mislabel.** `failover/ended` looked like rooms dying in the failover. In fact it's the reassigner's routine cleanup: when a match ends, the game server stops reporting the room, and the lobby asks a server to take it, gets NOT_FOUND and removes it. A range query showed it rising with the load test's room turnover, not at the drain.
- **A load generator on one address measures your rate limiter.** 160 players reconnected at once after the drain. Each resume is a join plus a WebSocket upgrade from the same per-address bucket (20/s, burst 40). About four 429s each, with exponential backoff, gave a resume p50 of 12 s. The drill's own players on a different address were back in 0.1–0.2 s. Same move, different bucket: that difference is the proof.
- **Reproduce before fixing.** The AWS logs were enough to suspect both causes, but the dev-box run turned each into a measured fact: raw 41 against increase 0, and the count of 429s after the stop.

### 6.11 Subdomain

- **A subdomain, not a path, when apps share a domain.** The apex was wanted for other experiments, so the app had to move. Under `icanfly.click/exp/doodle-arena/` it would share an origin with everything else on the apex: its `localStorage`, any script's reach into the page, a CSP that has to fit every app, and cookies that `Path` only partly separates. It would also need a base path in the web build, nginx and every absolute URL. `doodle-arena.icanfly.click` is its own origin, and the app didn't change at all: the certificate, the issuer, the OAuth redirect and the WebSocket origin check all came from one Terraform variable.
- **Same-site is not same-origin.** A sibling such as `blog.icanfly.click` can't read the app's cookies (auth sets them host-only, without `Domain=`), but it is the same site, so `SameSite=Strict` doesn't stop its requests, and it could set a cookie with `Domain=icanfly.click` that the app then receives ("cookie tossing"). The `__Host-` prefix prevents that but requires `Path=/`, and the refresh cookie is scoped to `/api/auth` on purpose. Accepted while one person runs every sibling; with untrusted siblings the answer is a separate registrable domain.
- **Two inputs that were one.** Terraform looked up the Route 53 zone by the app's name, which only works at an apex. The fix separates "where the app lives" from "which zone holds it", and the script finds the zone by trying the name's suffixes against Route 53 (exact name match, public zones only), so the command stays one variable long and a wrong guess fails with a clear error rather than a record in the wrong zone.

### Follow-up to 6.9: assets missing from the SLI

- **An SLI is a query, so test it like code.** The API SLOs filtered `http_route=~".*/api/.*"`. Django's OpenTelemetry instrumentation labels a route as its URL pattern, `api/assets/drawings`, without the leading slash that FastAPI, Spring and Go's mux give, so every assets request fell outside both SLOs. Nothing failed: the dashboard showed numbers and the alerts evaluated, just over three services instead of four. Light traffic to every service and a `sum by (service_name)` of the SLI's own selector showed the gap in a minute.
- **Check the denominator, not only the alert.** alerts-check proves a rule evaluates without an error, not that it measures what it claims. The fix (`/?api/.*`, anchored as every Prometheus regex is) is one optional slash; the lesson is to list which series a selector matches whenever a new service or framework joins.

### Docs sync after Stage 6

- **No test reads the design doc.** After six stages the code was right and the doc had drifted in three ways: stale numbers after a change elsewhere (the game servers moved from 0.25 to 1 vCPU, but the capacity paragraph still reasoned from 0.25), dead references (an ADR naming an admin route that was never built that way, "Secrets Manager" where everything is SSM), and omissions (new tables, events and error codes added task by task without a line in the doc). A review that reads every section claim by claim against the code found several dozen; the same review found no TODOs and no skipped tests.
- **Check the library, not the summary.** The doc's JWKS rule (refetch at most every 30 s, keep the last good set for an hour during an outage) holds for three services, and the review only noted that the marketplace "uses the stock decoder". Reading Spring Security 7.1's `NimbusJwtDecoder` showed what that means: a 5-minute cache, an unthrottled refetch on an unknown key id, and no grace at all, so an auth outage longer than 5 minutes refuses every marketplace token. That is now in the doc, and it is a follow-up, not a doc fix.

### CI hardening after Stage 6

- **Retry what is outside your control, and only that.** CI's failures with no code change were all at the edges: a Docker Hub 502, a Maven Central download that arrived corrupted (a digest mismatch, twice), and Testcontainers' reaper race between parallel Go packages. Each now has a narrow retry: image pulls before the tests, the agent download in its own stage, a container start, and a whole `make up` only when its log shows a registry error. A test failure is never retried, because a retried test is a flaky test you stopped seeing.
- **Pulling ahead doesn't protect a build.** Even with every base image already local, BuildKit asks the registry for each one's metadata during `docker build`, so a 502 still fails the build. That is why the stack job retries `make up` itself on a registry error, after `make down`, rather than trusting the pre-pull.
- **Find the list instead of maintaining it.** The pull script finds a suite's images by grepping its tracked code for pinned image names (a tag starting with a version number, which also rules out `kafka:9092`). A hand-kept list would go stale on the next new test container; a missed image here only loses the retry, never the test.

### Follow-up: the marketplace's JWKS rule

- **A library's defaults are a policy too.** Three services shared one rule for auth's keys: 10 minutes of cache, a refetch limit for unknown key ids, and the last good set kept for an hour while auth is down. The marketplace used Spring Security's `NimbusJwtDecoder` as it comes, which nobody had read: a 5-minute cache, an unthrottled refetch for any forged `kid`, and no outage grace, so an auth outage longer than 5 minutes would have refused every marketplace token. "Auth isn't on the hot path" (ADR 0001) was true for three services out of four.
- **Compose the library's parts instead of porting your own.** Nimbus has each piece: a TTL cache, refresh-ahead, a rate limiter and outage tolerance. Built from them, the marketplace's code is a builder and a counting wrapper for `authn.jwks.fetches`. The cost is two documented differences from the Go version (two fetches per window, and a request can wait for a refresh at expiry), which was the trade-off chosen over 150 lines of a third implementation.
- **Layered caches add up.** Nimbus caches the set an outage serves again for a full TTL, so an outage tolerance of an hour would have kept a withdrawn key for up to 70 minutes. Setting it to max-stale minus max-age (50 minutes) keeps the bound at an hour, at the price of a grace that can end as early as 50 minutes. The tests check the bound on a fake auth with the rule shrunk to seconds, and the dev box showed it on the real stack: with auth stopped and the rule at 60 s and 3 minutes, tokens kept working past the cache's expiry and were refused from 152 s.
